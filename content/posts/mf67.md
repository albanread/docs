_[WF32](/posts/wf32) shipped an assembler you could reach from the REPL, and I've
spent four articles watching that capability get lost and rebuilt. This is the one
where it earns its keep: Forth assembles the trampolines that let Cocoa call back
into Forth, and synthesizes a message-send thunk per ABI shape rather than
enumerating them._

## TL;DR

- **What:** "Objective Forth" — a fork of [MF66](/posts/mf66) pursuing one idea:
  **Forth as the Mac's system language.** Thirty commits, four days.
- **The thesis, from the design doc:** _"Cocoa is not a library Forth occasionally
  visits; it is the substrate Forth stands on."_
- **One object model.** MF66's native `kernel/oop.masm` is **retired**. A Forth
  class *is* an Obj-C class (`objc_allocateClassPair`), a Forth method *is* an IMP,
  a Forth instance *is* an `id`, fields *are* ivars. A Forth object and an
  `NSView` are the same kind of thing and can subclass across the boundary.
- **Forth emits its own callbacks.** `callback ( xt -- imp )` assembles an
  AArch64 trampoline from Forth, into a `MAP_JIT` arena, and seals it — turning a
  Forth word into a real C function pointer with **no Rust trampoline**. The
  commit calls it plainly: _"We are a macro assembler."_
- **Sends are synthesized, not enumerated.** One arm64 marshalling thunk per
  *(form, arg classes, return class)*, emitted on demand — replacing a fixed
  "thunk zoo" and unlocking mixed int+float signatures no fixed thunk could
  express.
- **The types come from a database.** `cocoa.sqlite` — the shared
  [cocoa_data](/posts/cocoa-data) mirror — supplies exact per-method AAPCS64
  register classification across **~482,000 runtime methods**. The ~0.6% of
  selectors that are genuinely ambiguous are resolved at send time by a runtime
  **PIC**.
- **It ships as an app.** `mf66 --app SRC.f -o NAME.app` packages a Forth+Cocoa
  program as a self-contained, double-clickable macOS bundle. WF32's `FSAVE`
  turnkey, back after twenty years and a change of operating system.
- **Get it:** [Downloads](#download-run) · [Source](https://github.com/albanread/MF67)

## Where it sits

[WF32](/posts/wf32) → [WF64](/posts/wf64) → [WF65](/posts/wf65) →
[WF66](/posts/wf66) → [MF66](/posts/mf66) → **MF67**. This is the end of the
Forth line as it stands. See the [timeline](/timeline).

MF67 inherits MF66 whole — the LLVM-free AArch64 token-IR optimizing compiler,
the deferred virtual-stack lowerer, the register pinning, the benchmarks — and
changes only what it takes to make Cocoa the substrate. The crate and binaries
are still named `mf66`, which tells you how much of it is inherited.

## The thesis

From `docs/design/forth-cocoa.md`:

> Goal: **program the Mac entirely from Forth.** Imagine Forth is all you have on
> the machine — you build IDEs, games, tools, and ordinary apps from it. Cocoa is
> not a library Forth occasionally visits; it is the substrate Forth stands on.

The README frames the motivation less formally, and I think more usefully:

> Also I have been recently exploring the concept of "let's use and explore the
> features of the operating system" as opposed to "let's ship a web browser and
> compile our app to JavaScript."

Three consequences are drawn out and then actually implemented, which is the part
that makes this worth reading rather than just agreeing with.

## Part 1 — one object model: a Forth class *is* an Obj-C class

MF66 had a perfectly good object system in `kernel/oop.masm` — classes,
instances, `self`, `(send)`, single inheritance. MF67 **deletes it**.

> MF66's native OOP … is *replaced* by Obj-C-backed objects … Defining a Forth
> class calls `objc_allocateClassPair`; a Forth method becomes an IMP (a Forth xt
> reached through the callback trampoline); a Forth instance is an `id`; fields
> are ivars. There is **one** object model and it is the Obj-C runtime's — so a
> Forth object and an `NSView` are the same kind of thing, can subclass across the
> boundary, and interoperate with no marshalling.

The decision is recorded with its cost attached, which I always want to see:

> The call: simpler for the user (one kind of thing you send messages to) over the
> efficiency of a dual model (dynamic dispatch + heap + refcount now apply to all
> objects).

Scope is bounded sensibly: only *objects* unify. Raw data — `variable`, `create`,
`allot`, cell arrays — stays plain static Forth memory, and field access still
compiles to a fixed ivar offset. Only *dispatch* is dynamic.

What it looks like:

```forth
class counter
  cell ivar: n
  :m init  0 to n ;m              \ self + ivar n are implicit; `to n` stores
  :m bump  n 1+ to n ;m
  :m val   n ;m
end-class

counter new c
c -> init
c -> bump   c -> bump   c -> bump
." counter after 3 bumps = "  c -> val  .  cr
```

And the proof, from the same example file — it isn't a Forth object that pretends,
it's an `NSObject`:

```forth
c s" isKindOfClass:" selector  s" NSObject" objc-class  msg1  255 and  .  cr
```

Ivars use **value semantics** — `n` fetches, `100 to n` stores, no `@`/`!`, `self`
implicit — which is a nice piece of dialect design: it reuses Forth's existing
`value`/`to` intuition rather than inventing accessor syntax.

## Part 2 — Forth assembles its own callbacks

This is the commit I'd point at if someone asked why any of the previous four
articles mattered.

For Cocoa to call *into* Forth — a `drawRect:`, a delegate method, a target-action
— a Forth word has to become a real C function pointer. The conventional answer is
a Rust trampoline. MF67 doesn't write one:

> **"We are a macro assembler"** — give Forth a code-emit surface and let it build
> the Cocoa callback trampoline itself, no Rust trampoline.

The mechanism is three words. `rt_code_emit` / `rt_code_seal` give Forth a
thread-local `MAP_JIT` arena to write AArch64 into and seal into executable
memory. `code-emit ( insn -- )`, `code-seal ( -- addr )` and
`call-imp ( arg imp -- result )` expose it. And then:

> Forth `callback ( xt -- imp )` emits `str x30,[sp,#-16]!` ; `movz/movk x9,xt` ;
> `blr x9` ; `ldr x30,[sp],#16` ; `ret`. A Forth word becomes a real C function
> pointer.

Five instructions, emitted by Forth, one at a time, into memory Forth then seals.
The commit notes why it works at all: the Forth VM registers are AAPCS64
callee-saved, so the machine state survives being re-entered from inside a Cocoa
callback.

Trace that capability backwards. [WF32](/posts/wf32) had `CODE … END-CODE` — an
assembler resident in the image, so you could define a primitive in x86 without
leaving the REPL. [WF64](/posts/wf64) lost it: the assembler became a build-time
tool, and inlining had to be hand-hexed as `mov byte ptr [r8+3], 0xF8` because the
running Forth couldn't call the thing it was built with. WF64 got a partial
version back late as `CODE:`. MF66 restored it properly. And here, four projects
on, that same capability is what lets a Forth program be a first-class Cocoa
citizen rather than a scripting layer on top of one.

The verification is headless and cheap: `' dbl callback 21 swap call-imp` → `42`.

## Part 3 — synthesizing the send

The second half of the macro-assembler thesis, and the more technically impressive
one.

`objc_msgSend` on arm64 is a single entry point for every signature — no `_stret`,
no `_fpret`, those don't exist on AArch64. But *calling* it correctly means
classifying every argument per AAPCS64 and putting it in the right register file:
integers and pointers into `x2…`, doubles into `d0…`, with the general and
floating-point register counters advancing **independently**. Structs by value
have their own rules again.

MF67's first approach was the obvious one — a zoo of fixed thunks: `osend1..4`,
`osend1f..4f`, `dsend1..4`. Then:

> Replace the fixed-thunk zoo with ONE per-shape send **SYNTHESIZED** into the JIT
> arena from the selector signature. … emits an arm64 marshalling thunk per
> `(form, arg classes, ret class)`: recv→x0, sel→x1 (**sel rides in TOS, never
> baked** — so one thunk serves every selector of the shape), GPR args → `x2..`
> and double args → `d0..` INDEPENDENTLY per AAPCS64 (NGRN/NSRN), bakes
> `objc_msgSend`'s address, calls, and delivers the result to the right Forth
> stack.
>
> **This is the macro-assembler thesis: we don't enumerate shapes, we emit them.**

The detail that makes it economical is the one in bold: the *selector* rides in
TOS rather than being baked into the thunk, so a thunk is cached per ABI *shape*,
not per method. A few dozen thunks cover the whole framework.

And it unlocked signatures the fixed zoo structurally could not express — the
mixed integer/float shapes:

```forth
" Helvetica" 24.0e0 NSFont -> fontWithName:size:        \ (@d)
0.5e0 blue red -> blendedColorWithFraction:ofColor:     \ (d@)
[ NSFont fontWithName: " Courier" size: 18.0e0 ]        \ the DSL, same engine
```

Struct-by-value came next in two commits — arguments (`NSRect`/`NSPoint`/`NSSize`)
and returns (HFA plus `NSRange`) — which is the part of AAPCS64 that actually
bites.

The verification is worth quoting because it's the right way to check a code
generator:

> the impl pass **disassembled the emitted words with `llvm-mc`** and confirmed
> them byte-for-byte vs the hand thunks (0 bugs).

The new synthesizer was proven equivalent to the hand-written thunks it replaced,
byte for byte, before those were retired. That is the same differential instinct
as [WF65 as WF66's oracle](/posts/wf66) and [WF66 as MF66's](/posts/mf66),
applied at instruction granularity.

## Part 4 — where the types come from

A synthesizer needs to know each method's shape, and there is no way to derive
that from a selector name. So MF67 reads it from a database — and the database is
one this portfolio already had.

`src/cocoadb.rs` is a thin binding onto `cocoa.sqlite`, the shared
[cocoa_data](/posts/cocoa-data) mirror of the macOS SDK:

> Replaces the old embedded `cocoa-selectors.json`: full coverage (**all ~482k
> runtime methods**, not 5.6k) and an *exact* per-method AAPCS64 register
> classification, rather than a flat, lossy selector→kind projection. The
> `method_abi` table gives, per `(class, selector)`, a return token and one token
> per argument:
> `g` gpr/id · `f` fp/double · `h1..h4` HFA · `i1 i2` small int-struct · `b` byref
> · `s` sret · `v` void · `?` unmodelable

Two things about that. First, the jump from 5,600 hand-curated selectors to
482,000 machine-extracted ones is the difference between a curated shim and the
"comprehensive, not curated" goal the design doc set. Second, note the `?`
token — *unmodelable* is a value in the schema. The database says when it doesn't
know, rather than guessing.

### The 0.6% that can't be resolved statically

Some selectors have more than one ABI shape across classes. `size` returns an
`NSSize` struct on one class and a plain cell on another; from a bare stack
receiver the compiler cannot tell which. MF67's answer is a **runtime polymorphic
inline cache**:

> at SEND time, recover the object's class from its isa (`object_getClassName`),
> resolve the EXACT `(class, selector)` shape, synthesize/cache the matching
> thunk, and hand it back for the caller to `execute`. Class-exact late binding —
> using the runtime we already are. Only the **~0.6%** of selectors that are
> actually ambiguous are routed here; the rest stay on the fast compile-time
> by-name thunk.

A PIC in a Forth, resolving Objective-C ABI shapes, keyed on
`(class, form, arity, selector)`. Note the reuse in "using the runtime we already
are" — MF67 doesn't build class metadata, it asks the Objective-C runtime it is
already living inside.

## Part 5 — the surface

Two send syntaxes, both compiling to the same thing.

**RPN**, which is just Forth:

```forth
win " Hello" setTitle:
NSApplication -> sharedApplication  value app
```

**The `[ … ]` keyword DSL**, for Cocoa's long selectors, where reading arguments
next to their keywords genuinely helps:

```forth
[ dict setObject: " val" forKey: " key" ]
[ names addObject: " alice" -> uppercaseString ]      \ args are full RPN
```

It is overloaded onto Forth's existing `[ … ]` and disambiguated **by shape**: a
send contains a `keyword:` token (the first one ends the receiver expression); a
bracket with no keyword is still the classic interpret-state switch. So this keeps
working, in the same file:

```forth
: answer  [ 6 7 * ] literal ;
```

Overloading a core piece of Forth syntax is a bold call. The disambiguation rule
is simple enough to hold in your head, which is the only thing that makes it
defensible.

And the types are Cocoa's types, all the way down: **`NSString` is the string
type** (`" …"` is an NSString literal; `s" …"` is raw bytes, demoted to plumbing
for class and selector names), collections are `NSArray`/`NSDictionary`, and `.`
is object-aware — an object prints its `description`.

That is a real decision with teeth: MF67 has *no Forth string library*. Text is
Foundation's problem.

## Part 6 — a window, in Forth, that ships as an app

`examples/app-window.f`, in full, is a native macOS window with nothing
underneath it but message sends:

```forth
NSApplication -> sharedApplication  value app
0 app -> setActivationPolicy:

NSWindow -> alloc
  s" initWithContentRect:styleMask:backing:defer:" selector
  15 2 0   0e 0e 480e 320e   msgrect3   value win

" Forth on Cocoa"  win -> setTitle:
0.12e0 0.14e0 0.18e0 1.0e0  NSColor -> colorWithRed:green:blue:alpha:  value bg
bg win -> setBackgroundColor:

win -> center  drop
0 win -> makeKeyAndOrderFront:  drop
-1 app -> activateIgnoringOtherApps:  drop

app -> run  drop                                    \ the Cocoa event loop (blocks)
```

There is no Rust GUI helper in that listing. `[NSApp run]` — the actual Cocoa
event loop — is sent from Forth. The design doc insisted on this:

> If a job *can* be done in Forth, it is — so we do **not** vendor the high-level
> helpers; we reuse only the dlsym/ABI *insight*.

And then it ships:

```bash
mf66 --app examples/app-window.f -o Window.app
open Window.app
```

The bundle contains a byte-identical copy of the engine (so its ad-hoc signature
survives — no re-signing), the source as `Resources/main.f`, and
`Resources/cocoa.sqlite` so the bundle is self-contained. On launch the engine
detects it is inside a bundle and runs `main.f` on the main thread. The commit
confirms a *moved* bundle still runs, which is the actual test of
self-containment.

[WF32](/posts/wf32) had `FSAVE` — write your live session out as a standalone
`.exe`. Twenty years, four rewrites and an architecture change later, the turnkey
is back, and what it produces is a double-clickable Mac app.

## Part 7 — the price of one object model

Unifying on Objective-C objects means inheriting Objective-C's memory management,
and the design doc explains why there was no alternative:

> Objc refcounting, no tracing GC (**the Forth stacks are untyped cells — can't
> distinguish an `id` from an int, so a GC can't find roots**).

That is the exact finding [MF66's adversarial critique](/posts/mf66) made about
`newgc-core`: a precise moving collector infers pointer-ness from tag bits, and
Forth cells have no tags. In MF66 it was a scoping decision about which heap the
GC owns. Here the same fact decides the object model's lifetime discipline
outright.

The scheme is stated with its 90/10 split visible: an autorelease pool per REPL
turn and per Cocoa event or frame does the boring majority; `new` returns an owned
`+1` reference; **stored** references (ivar, variable, global) retain on store and
release on overwrite; **stack** ids are borrowed and never auto-retained; explicit
`retain`/`release`/`autorelease` for the rest.

It's a coherent design. It is also the point where Objective Forth stops being
"Forth with a nice library" and becomes a dialect with rules you have to learn.

## Part 8 — the last session, which is the honest one

The final commit is a debugging story, and the message is the best-written thing
in the repository:

> Three interlocking pieces from one investigative session: chasing a crash in the
> Forth-native IDE led to guard pages, which surfaced latent bugs, which led to
> compiler-verified stack-effect checking, which found more bugs — verified
> against the IDE again at the end.

The 8 MB Forth region was a plain heap allocation with the data stack, return
stack and locals stack **packed back-to-back with zero gap** — so an overflow on
one silently corrupted the next. No crash, no signal, just quiet cross-stack
corruption. The fix is to `mmap` the region so it can be `mprotect`ed, and put a
`PROT_NONE` guard page at every boundary.

Two consequences I'd frame for anyone doing similar work:

1. **Turning the guard pages on surfaced two pre-existing bugs immediately.**
   `USER_FP0`/`USER_FSP` and `USER_HOLD`/`USER_HOLD_END` were computed relative to
   the region base instead of the user-area base — harmless only because they
   happened to alias into a rarely-touched corner of the data stack. The new guard
   page occupied exactly that space and turned a latent aliasing bug into an
   immediate, correctly-attributed fault at boot.
2. **Guard pages are page-granular, and that isn't fine enough.** A single stray
   `drop` doesn't reach the next page. So there is one precise bounds check per
   `call()` — not per primitive — plus a `TOP_SLOP` headroom allowance because
   `forth_main`'s prologue legitimately reads one ambient cell past "empty" by
   protocol. The original `0e drop` repro, which used to abort the process, now
   degrades to a recoverable Forth error and the session keeps working.

Then the compiler was pointed at the class of bug guard pages *can't* catch — a
wrong-but-non-empty stack — using stack-effect information the optimizer was
already computing for its own purposes. Warning-only, and it found more bugs.

That is a good closing note for this whole series: the optimizer's bookkeeping,
built to make code faster, turns out to be the thing that can tell you your code
is wrong.

## What works, and what's open

- **188 tests across 58 suites**, on top of everything [MF66](/posts/mf66) had.
- Classes, methods, ivars, `super` (including multi-argument), the DNU bridge
  (an unrecognized selector throws `-2058` rather than crashing), typed returns,
  struct arguments and returns, collections, `NSString` as the string type, the
  `[ … ]` DSL and its `_f_`/`_n_` argument patterns.
- `.app` packaging, a child-engine subprocess as the two-process IDE foundation,
  and a tabbed Forth-native IDE.
- Open in the working tree at the time of writing: turnkey/AOT boot work
  (`kernel/turnkey_boot.masm`, `tests/turnkey_aot.rs`) — uncommitted, so treat it
  as direction rather than fact.

The status field says "exploratory" and that's right. This is four days of pushing
one idea hard, not a settled product.

## Download & run

Prebuilt Apple Silicon binaries: the
[GitHub Releases page](https://github.com/albanread/MF67/releases).

```bash
git clone https://github.com/albanread/MF67
cd MF67
cargo build --release
./target/release/mf66 examples/objective-forth.f
```

Cocoa examples need the main thread, so run them directly rather than through a
harness. To package one:

```bash
./target/release/mf66 --app examples/app-window.f -o Window.app
```

The engine wants `cocoa.sqlite` from the sibling [cocoa_data](/posts/cocoa-data)
repo (`$COCOA_DATA_DB`, else `../cocoa_data/cocoa.sqlite`). Without it the binary
still runs — sends just fall back to the untyped integer/cell default.

## Notes, dead-ends, lessons

**A resident assembler is not a luxury.** Four articles of this series are about
losing [WF32](/posts/wf32)'s ability to assemble code from the running system and
slowly earning it back. MF67 is what it's *for*: emitting callback trampolines and
synthesizing per-shape message-send thunks are both things you simply cannot do
from a build-time assembler.

**Emit shapes, don't enumerate them.** The fixed thunk zoo was tractable right up
until mixed int/float signatures, which it could not express at all. The
synthesizer is less code, covers more, and is provably equivalent to what it
replaced.

**Machine-extracted metadata beats a curated list.** 5,600 hand-picked selectors
versus 482,000 with exact register classification. The curated list is a
prototype; the database is the product. Having built [cocoa_data](/posts/cocoa-data)
for another language entirely is what made this a two-day job.

**Unify the object model or don't — but pay the bill deliberately.** Retiring
`kernel/oop.masm` bought "one kind of thing you send messages to" and cost
dynamic dispatch, heap allocation and refcounting on every object. Both halves of
that are written down before the code was.

**Guard pages find bugs that already existed.** Two latent base-pointer errors
became immediate, correctly-attributed boot failures the moment there was a page
that would fault. Instrument first; the bugs are already there.
