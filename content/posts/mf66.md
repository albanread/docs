_A Forth that started as [WF32](/posts/wf32) in a Windows console, spent a while
trapped inside an LLVM macro assembler, and arrives on Apple Silicon having to
give up the single oldest trick in its inheritance: the return stack can't be the
hardware stack any more._

## TL;DR

- **What:** an Apple Silicon (macOS arm64) re-implementation of
  [WF66](/posts/wf66)'s token-IR optimizing STC Forth, JIT-compiled through
  JASM's **LLVM-free AArch64 backend** (`wfasm::a64` + `MacJit`'s `MAP_JIT`
  loader). **No LLVM at build or run time.** 101 commits, three days.
- **Strategy:** a *retarget*. WF66 splits into an architecture-neutral front-end
  + token-IR reducer over an x86-specific back-end; MF66 keeps the neutral half
  and rebuilds the AArch64 half.
- **What broke:** [WF32](/posts/wf32)'s founding trick. On x86 the Forth return
  stack *is* `rsp` — `>r` is `push`, `;` is `ret`, STC is free. On AArch64 `bl`
  puts the return address in **x30, not on a stack**, so MF66 carries an explicit
  return stack in `x28` and leaves `sp` permanently 16-aligned for the ABI.
- **What it gained:** arm64's register file. Everything load-bearing is
  **callee-saved** — so the promotion pool survives calls *unconditionally*,
  where WF66 had to barrier-check caller-saved `r10`/`r11`.
- **The headline:** WF66 declared its optimizer complete and named the one gap it
  would not close — loop-carried register residency. **MF66 closed it**, with
  cross-iteration pinning for both float and integer locals, gated by a
  call-safety classifier.
- **Measured, LLVM-free:** ~**2.6× slower than `clang -O2`**, ~**22× faster than
  CPython 3.14** (geometric mean) across integer/memory workloads — and on a
  tight 64-bit LCG loop it **matches C at 1.02×**.
- **Get it:** [Downloads](#download-run) · [Source](https://github.com/albanread/MF66)

## A retarget, not a rewrite

The README states the strategy as a table, and the honesty of it is the point:

| Reused | From |
|---|---|
| AArch64 encoder + `MAP_JIT` loader | [JASM](/posts/jasm) (`a64` + `native_macos`) |
| GC (`newgc-core`) | [MacNCL](/posts/macncl) |
| Native Cocoa IDE (`mf66ide`) | a `macos_panes_ide` fork |
| Forth front-end + token-IR reducer | [WF66](/posts/wf66) |

New work: the AArch64 lowering leg of the back-end, the STC kernel translated
primitive by primitive, the runtime-substrate swaps, and the GC/IDE glue.

This is the [shared substrate](/posts/shared-substrate) paying out. By the time
the Forth line wanted to be on Apple Silicon, the encoder, the JIT loader, the
collector and the IDE shell already existed there because four other languages had
needed them first. MF66 is three days of work because roughly half of it was
already sitting on disk.

## The thing that didn't survive the port

Go back to [WF32](/posts/wf32) for a moment. Its whole case for subroutine
threading rests on one architectural fact:

```forth
code >r ( n -- r: n )
      push    eax
      next; inline
```

`>r` is a single `push`. The Forth return stack **is** the x86 hardware stack, so
`call` pushes to it, `ret` pops from it, and there is no inner interpreter because
the CPU already implements one. That property is inherited unbroken through
[WF64](/posts/wf64) (`rsp`), [WF65](/posts/wf65) and [WF66](/posts/wf66).

AArch64 does not work that way. `bl` writes the return address into **x30**, a
register — nothing is pushed. There is no hardware stack discipline to borrow. So
MF66 maintains the return stack explicitly:

| role | WF32 → WF66 (x86) | MF66 (AArch64) |
|---|---|---|
| return stack | `rsp` — the CPU stack | **`x28` (RP)** — an explicit full-descending stack |
| C stack | — | `sp`, kept permanently 16-aligned for `bl`/`blr` |
| `>r` | `push rax` | `str TOS, [RP, #-cell]!` |
| nest / unnest | implicit in `call`/`ret` | `str x30,[RP,#-cell]!` … `ldr x30,[RP],#cell ; ret` |

The `sp` decoupling isn't optional: AAPCS64 requires `sp` 16-byte aligned at every
call, and a Forth return stack pushing 8-byte cells would violate that constantly.
So the two stacks separate.

The porting guide notes the compensation, which is real — return-stack words get
*simpler*, because they no longer have to step around a return address sitting in
the middle of the data they want. `>r` is one store, not a juggle.

Still: four projects and two decades after WF32, the single structural inheritance
that justified the whole design is the one the instruction set took away. The
architecture survived; the argument for it had to be made again.

## The ABI, and what a bigger register file buys

`src/abi.rs` is 71 lines and the best-documented file in the project — every
register choice justified against AAPCS64, with a unit test asserting the pools
are disjoint and contain nothing forbidden.

```
TOS  = x0     DSP = x19    UP  = x20    LP = x21
FTOS = d8     FSP = x22    RP  = x28
FUSION_POOL    = x9 … x15          (caller-saved, window-local)
PROMO_POOL     = x23, x24          (callee-saved)
FP_PROMO_POOL  = d9 … d15          (callee-saved low 64)
FORBIDDEN      = x16, x17, x18
```

The governing rule: **everything that must survive a settle-barrier call is
callee-saved.** The upgrades over WF66 are called out one by one in the comments:

- **`LP` becomes callee-saved** (WF66's locals pointer was caller-saved `r15`).
- **The promotion pool becomes callee-saved** — `x23`/`x24`, so promoted values
  survive barriers *unconditionally*. WF66 used caller-saved `r10`/`r11` and had
  to barrier-check every promotion.
- **The fusion pool grows to seven registers** from WF66's six, which "gives
  `window_fuse` more freedom."
- **Seven callee-saved FP registers** (`d9`–`d15`) for values that must survive a
  libm call inside a window.

That is the arm64 register file translating directly into optimizer freedom.
x86-64 has 16 GP registers of which a handful survive a call; AArch64 has 31 with
ten callee-saved, and MF66 spends them on exactly the passes that were constrained
before.

`FTOS = d8` carries a documented trap: `d31` would be *wrong*, because it is
caller-saved and clobbered by every libm call. And only the low 64 bits of
`d8`–`d15` are preserved — never the full 128-bit `q8`. That distinction is
enforced by a CI lint, not by hoping.

## One compiler, not two

The other structural change is stated plainly in `compiler.md`:

> The ancestor system, **WF66**, is structured as *two* pieces: a Forth compiler
> … and a separate Rust optimizer that consumes that IR … Two stages, two
> implementation languages, a serialized IR handed across the boundary. **MF66
> collapses this into a single optimizing Forth compiler, entirely in Rust.**

So when MF66's recognizer sees `+`, it emits `Tok::Bin(Add)` — an optimizable
token — rather than a call to a `+` primitive. "The decision of what can be
optimized lives in one place (`build_vocab`), shared by recognition and lowering."

This is cleaner, and it costs something worth naming. [WF66's](/posts/wf66) best
safety property was **two sources of truth**: the eager WF65 body was always
compiled underneath, so a span the optimizer couldn't model simply kept its
correct body. Collapsing to one compiler removes that net — there is no second
implementation to fall back to. MF66 buys the safety back differently, with a
differential corpus (below) and a `Call` token that is the universal escape hatch
for anything the vocabulary doesn't recognise. A reasonable trade, made
deliberately — but a trade.

## The deferred virtual stack — one step past WF66

This is where MF66 is genuinely a better compiler than its parent, and it follows
the family principle one level further.

[WF32](/posts/wf32) deferred *literals* — a compile-time stack of constants,
flushed by `sync-code`. [WF66](/posts/wf66) deferred *emission* — tokens
optimised as data, lowered to asm text, then reduced again as instruction records.
**MF66 defers the entire stack.**

```rust
vs:  Vec<Loc>     // data stack window;  Loc = Const(i64) | Reg(u32)
fvs: Vec<u32>     // FP stack window;    d-registers
```

The consequences, in the doc's own words:

- **Constants are deferred.** `Lit(5)` pushes `Loc::Const(5)`. The 5 materialises
  only if something consumes it as a register operand — "and often it never is."
- **Stack motion is free.** `dup`, `swap`, `over`, `rot` are *re-indexing of
  `vs`*, not instructions. `swap` exchanges two `Vec` entries and **emits
  nothing.**
- **ALU ops reuse registers**, allocating from the pool only when needed.

Read that middle point against the rest of this series. [WF65](/posts/wf65) spent
nine commits and a measurement harness getting `swap` down from a 5-byte call to a
few register moves, and counted it a win — correctly. MF66 compiles `swap` to *no
instructions at all*, because the stack being shuffled is a compile-time data
structure that only becomes machine state at a settle.

A **settle** writes the virtual stacks back to canonical form — data top in `x0`,
the rest stored down from `[DSP]` with a single pointer adjust, FP top in `d8` —
and it happens in exactly two places: **before every `Call`**, and at the end of
each straight-line run. So:

> The whole optimization payoff is **doing real work between settles and emitting
> as few of them as possible.**

And the simplification that keeps it tractable: `compile_control` flushes the
pending token run at every control-flow boundary, so **the lowerer only ever sees
straight-line code.** No branches, no CFG, no dataflow — the same
refusal-of-machinery instinct as WF66, applied again.

## Closing the gap WF66 declared closed

[WF66's README](/posts/wf66) ends with an unusually clean statement of a known
limitation:

> The residual ~2.6× off MASM is one thing: **loop-carried register residency.**
> … That gap is left open by choice — the optimizer work is complete.

MF66 closed it. Two commits — *cross-iteration register pinning for float locals*
and *cross-iteration pinning for integer locals (GP twin of fpins)* — do exactly
the thing WF66 declined:

- Within a run, caches keep hot locals and `fvariable`s resident. But caches are
  per-run, so a loop back-edge resets them and a loop-carried local reloads every
  iteration. That is the WF66 behaviour.
- **Pinning** binds the loop's float locals to fixed `d`-registers and its integer
  locals to high GP registers for the loop's whole duration: a one-time load
  preamble before the loop, registers reserved across every run of the body
  (re-reserved after each settle), reads and writes becoming `fmov`/`mov` instead
  of frame traffic, and a one-time spill epilogue where the loop exits.

The soundness gate is the part worth pointing at. `pin_safety` classifies every
word in the loop body:

| class | meaning | what survives |
|---|---|---|
| `Full` | no call anywhere in the body | float **and** integer pins |
| `FpOnly` | an FP-preserving libm call (`fsin` etc.) whose wrapper preserves callee-saved `d8`–`d15` but clobbers GP scratch | float pins only |
| `Barrier` | anything else | no pinning |

That three-way split is only *possible* because of the ABI work above — you can
only claim "float pins survive a libm call" if the pins are in callee-saved
registers and you know the wrapper's contract. WF66 couldn't make that claim on
x86-64 with the register budget it had.

Note too the framing WF66 itself supplied and MF66 honours: register residency is
only ever valid inside a **call-free region**. This is not whole-program register
allocation — it is the same boundary hand-written assembly exploits, now available
across a loop instead of only within a run.

## How the kernel was actually ported

Not by hand-waving. `docs/porting-guide.md` documents a differential method:

> The kernel was ported from WF66's x86 procs primitive-by-primitive against a
> 150-file **differential corpus** (`tests/data/direct/`, the day-one oracle):
> translate the x86 proc → AArch64, adversarially verify it, then the word's `.t`
> flips NYIMP → PASS (PASS = matches WF66's observed behavior).

So [WF66](/posts/wf66) becomes MF66's oracle exactly as [WF65](/posts/wf65) was
WF66's — each project in this line freezing its predecessor and diffing against
it. The guide hands translators a register map, a `stk(in, out)` contract
("**always declare `stk` with the same `(in,out)` WF66 used**"), an idiom
translation table, and the forbidden-register list backed by a `kernel_lint` test
that fails the build.

Status is stated per layer rather than as a claim about the whole: integer,
memory, string, number and floating-point are ported and verified; **object
dispatch (`self`) is the remaining frontier.**

## The review that happened before the code

`docs/review/` holds something I wish more projects had: a subsystem review plus a
genuinely adversarial critique of the port plan, written against the real
substrate *before* the port started. Four findings, all load-bearing:

1. **The GC's root model doesn't fit Forth.** `newgc-core` is a precise, moving
   collector that decides pointer-ness by inspecting tag bits in each word — the
   Lisp model. Forth data-stack cells are **untagged raw 64-bit integers**, so an
   integer that happens to look like a tagged pointer would be "evacuated" into
   heap corruption. The critique rejects the plan's "~30–50 lines, defer to
   MacNCL" estimate and re-scopes it: the GC must be precise over the *tagged
   managed heap only*, with a hard invariant that every managed handle on the data
   stack always carries its tag.
2. **x16 is not free at call sites.** The plan assumed it was; `MacJit`'s far-call
   veneers emit `movz/movk x16; br x16` at relocation time, so x16 is dead across
   every call — including the implicit ones the loader inserts.
3. **x18 is enforced nowhere.** The AArch64 encoder will happily emit the Darwin
   platform register; nothing but discipline stands between a hand-written kernel
   and an intermittent silent crash. Fix: a mechanical CI grep gate.
4. **The optimizer's cost model is x86-shaped.** `promote_hot_cells` and
   `window_fuse` assume a folded `op reg,[rbp+disp]` is *one* instruction; on
   fixed-width AArch64 it is `ldr` + `op`. The break-even for promotion and fusion
   is different, so the passes could *pessimize* while remaining correct. Also
   flagged: the instruction AST models no NZCV liveness, because on x86 flags were
   an implicit micro-detail the IR never had to track.

All four are visible in the shipped code. `FORBIDDEN` contains x16, x17 and x18
with a unit test; the README advertises a grep gate enforcing the x18 / `q8`–`q15`
ban; the register pools were re-chosen around callee-saved survival. That
traceability — critique to constant to test — is the part worth copying.

## The numbers

![MF66 Forth vs C (−O2) vs CPython 3.14 — compute time per benchmark, log scale](/images/mf66/benchmarks.svg)

| benchmark | MF66 Forth | C `-O2` | CPython 3.14 | vs C | vs Python |
|---|--:|--:|--:|--:|--:|
| `fib(34)` recursive | 19.5 ms | 8.6 ms | 385 ms | 2.25× slower | 19.8× faster |
| `collatz` Σ steps 1..10⁶ | 357 ms | 93 ms | 5366 ms | 3.83× slower | 15.0× faster |
| `sieve` < 10⁶ (π = 78498) | 4.5 ms | 0.9 ms | 58 ms | 5.0× slower | 12.8× faster |
| `lcg` ×10⁸ (64-bit) | 100 ms | 98 ms | 6205 ms | **1.02× ≈ C** | 61.8× faster |

The README's framing is the right one:

> What makes the numbers interesting is what's *not* underneath them: **no LLVM.**
> `clang` stands on LLVM's decades of optimization passes and register allocation;
> MF66 compiles through its own hand-written AArch64 encoder … with a single
> token-IR reduce pass and a deferred stack lowerer.

Methodology lives in `bench/BENCHMARKS.md` with a one-command reproducer:
best-of-5, each language timed on its own compute-only monotonic clock, identical
results across all three, and — the part that matters — the C and Python ports
passed an **adversarial fairness audit**, with `cc -O2 -S` inspected to confirm
the loops aren't constant-folded away. Same benchmark discipline as [the
Smalltalk-on-Dart work](/posts/optimizing-smalltalk-on-dart), and it is why the
`lcg` row is quotable rather than embarrassing.

There is also a **terminal tail-call** optimisation that turns self-recursion into
an O(1)-return-stack loop: a 10⁸-deep tail-recursive LCG runs at 1.49× a
`DO`/`LOOP` with a bit-identical result — where without it the return stack would
simply overflow.

And `compiler.md` is candid about where the remaining distance to C comes from:

> The gap between MF66 and a heavyweight optimizer is *structural*, not a missing
> pass: it is the per-call settle, the `fmov`/`mov` copies when reading pinned
> locals, and the do-loop counter overhead — the price of the STC model and the
> two-stack discipline. The optimizer's job is to minimize how often that price is
> paid; it cannot make a `Call` free.

## What else is in there

- **`CODE` … `END-CODE`** — hand-written AArch64 primitives assembled through
  JASM from the running Forth, with a benchmark comparing the escape hatch against
  the optimizer and against C. [WF32](/posts/wf32) had a resident assembler from
  the start; the line has now had one back for two projects.
- **A native Cocoa IDE** (`mf66ide`, packaged as a self-contained `MF66.app`) on
  the shared macOS panes shell, with a rope-backed syntax-coloured editor,
  selection, clipboard, undo/redo and native file dialogs.
- **A TCL agentic control layer** plus headless screenshots for the workspace —
  see [the role of Tcl for agents](/posts/tcl-for-agents).
- `marker`/`rollback` and `forget` for interactive development; `defer`/`is`,
  `2value`, `case`/`of`, `REPLACES`/`SUBSTITUTE` and a long tail of Forth-2012
  parity words.
- **169 tests across 58 suites**, including ANS conformance, the direct
  differential corpus, and per-subsystem tests for the optimizer, floats, locals,
  inlining and immediate chaining.

Line counts: ~10.4k lines of Rust (the optimizer `opt.rs` is 2,109 of them, the
session 3,053), a hand-written AArch64 `.masm` kernel, and 403 lines of
`compiler.md` explaining how it fits together.

## Notes, dead-ends, lessons

**A port is where you find out which of your properties were free.** WF32 got
subroutine threading for essentially nothing because x86's `call`/`ret` already
maintained the return stack. On AArch64 that subsidy doesn't exist, and MF66 pays
for it in explicit `str`/`ldr` pairs and a second stack pointer. The design still
wins — for different reasons than the ones originally written down.

**Defer one level further than you think you can.** WF32 deferred literals; WF66
deferred emission; MF66 defers the stack itself, and gets `swap` for zero
instructions. Each of those looked like the last step available at the time.

**Review the plan adversarially before writing the code.** The GC/untagged-cells
finding would otherwise have been a heap-corruption bug discovered weeks later at
random; instead it was a scoping decision made on day zero. Four findings, all far
cheaper to fix in a document than in a debugger.

**Freeze the predecessor and diff against it.** WF65 was WF66's oracle; WF66 is
MF66's, via a 150-file corpus where each word flips NYIMP → PASS only once its
observed behaviour matches. Three projects running, same discipline.

**State the remaining frontier.** "Object dispatch (`self`) is the remaining
frontier" tells a reader more than any amount of feature-list confidence — and it
is precisely what [MF67](/posts/mf67) picks up.
