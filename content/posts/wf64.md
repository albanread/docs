_[WF32](/posts/wf32) fit in 15,500 lines of Forth and inlined half its primitives.
WF64 is three languages and 45,000 lines, and its first act was to throw the
inliner away. This is the honest account of what a port costs._

## TL;DR

- **What:** a 64-bit **subroutine-threaded (STC)** ANS Forth for Windows x86-64,
  ported from [WF32](/posts/wf32)'s primitives and STC compiler. **69 commits over
  three weeks** (2026-05-19 → 06-10), M1–M7 complete, **ANS Forth-2012 core suite
  passing**, 353 Rust integration tests green.
- **How:** ~12,000 lines of hand-written `.masm` kernel, assembled and JIT-loaded
  at process start through **[JASM](/posts/jasm)**, which at this point rode
  **LLVM-MC + MCJIT** — so WF64 shipped a stock **67.7 MB `LLVM-C.dll`**, later
  beaten down to 10.2 MB by a custom X86-only build.
- **What was ported:** the register ABI, the `in/out` stack-effect annotations,
  the `tail-call` variable, and WF32's ten-field header transcribed cell for cell
  — via `src/wf32_port.rs`, a **793-line mechanical translator** from WF32's
  Forth-assembler syntax to JASM `.masm`.
- **What was dropped:** the inliner. The port tool records WF32's `inline` flag
  and then discards it, in as many words: _"WF64 doesn't inline primitives (every
  call is a real CALL)."_ It took three separate attempts to get it back.
- **The pattern that defines WF64:** WF32 optimised from *data it still had* — a
  compile-time literal stack, a per-word code generator. WF64 optimises by
  **decoding the machine code it just emitted** and rewriting it. Its own design
  doc names the flaw: the peephole _"re-derives information we already have."_
  That sentence is the reason [WF66](/posts/wf66) exists.
- **Get it:** [Downloads](#download-run) · [Source](https://github.com/albanread/WF64)

## Where it sits

The Forth lineage runs **[WF32](/posts/wf32)** (Alex McDonald, adopted as the
seed) → **WF64** → [WF65](/posts/wf65) → [WF66](/posts/wf66) →
[MF66](/posts/mf66) (Apple Silicon) → [MF67](/posts/mf67). WF64 is the
"reborn at 64-bit" step, and the high-water mark of the line's LLVM dependency.
See the [timeline](/timeline).

To read this article you don't strictly need [the WF32 piece](/posts/wf32), but
everything below is a comparison against it, so it helps.

## Why it exists, in the README's own words

> _"Writing the Forth compiler in Rust, like the other compilers here, was not
> satisfying — Forth does not fit well there. The shape is much better if we write
> Forth in masm. For this we build a macro assembler."_

That is the whole causal chain, and it is worth sitting with, because it explains
a project that otherwise looks like an odd detour. I did not set out to build an
assembler. I set out to build a Forth, discovered that a Forth expressed as Rust
data structures is a miserable thing, decided the kernel wanted to be assembly —
and therefore needed a macro assembler that could read `.masm` files and JIT them.
That assembler is [JASM](/posts/jasm), and WF64 is simultaneously its first
customer and its reason for existing.

The layer cake the README draws:

```
MASM kernel — assembly language (can invoke Windows API)
ANSI Forth Core — some MASM, some high level
ANSI Forth in Forth
Escape hatch — CODE: uses MASM
Escape hatch — LET infix expressions
Paged garbage collector
New strings
Interactive Forth REPL
User application
```

WF32 has almost the same cake. The difference is that WF32 baked it in one
language.

## What "ported from WF32" actually means

There is a file in this repo that makes the relationship unusually concrete:
`src/wf32_port.rs`, 793 lines of Rust whose entire job is to read
`gkernel32.fs`, find a named `code … next;` block, and print a ready-to-paste
JASM `proc(…) … endp()`.

Its doc comment is a compact summary of WF32's assembler syntax, written by
someone who had to make a parser for it:

- operands are space-separated, no commas — `mov ecx eax`
- memory is `{ … }` not `[ … ]`, ordered `[disp] base [index *scale]`
- size qualifiers precede the expression with no `ptr` — `movzx eax byte { eax }`
- immediates can be RPN — `sar eax cell 8 * 1-` means `sar eax, (cell*8)-1`
- stack effect is declared once as `N M in/out`

It is deliberately partial, and honest about it: RPN immediates get a `; TODO:`
flag rather than a wrong answer, user-area variable names are left alone for a
human to rename, and Forth names like `>r` get default `to_r` mangling that the
caller can override. The commentary explains why it's a translator and not a
build-time generator:

> _"Keeping the .masm files purely native asm (no runtime dependency on the WF32
> source) means a future reader can read what's actually executing without
> bouncing through a generator."_

That is the right call, and it is also the first crack. WF32's kernel *is* its own
generator — the source you read is the source that runs. WF64 chooses a
transcription, and from that moment the two systems can drift.

There is even a detail about reading the source at all: `gkernel32.fs` is
Windows-1252, not UTF-8, so the tool reads raw bytes and maps each to a codepoint
rather than risk a decode failure on the box-drawing characters in the comment
banners. Twenty-year-old source has texture.

### The line in the port tool that decides the next six weeks

```rust
/// True if the WF32 source flagged this primitive `inline`.
/// Informational only; WF64 doesn't inline primitives (every call
/// is a real CALL).
pub inline: bool,
```

And in the emitter:

```rust
if block.inline {
    out.push_str("; (WF32 marked this `inline`; WF64 makes every primitive a real CALL — irrelevant here.)\n");
}
```

108 of WF32's 201 primitives carry that flag. All 108 came across as comments.

I do not think this was a mistake, exactly — it is the correct order of work. Get
it running, get it correct, get the ANS suite green, *then* optimise. But it means
the ported system started life materially slower than the thing it was ported
from, and the rest of WF64's history is the story of clawing that back.

## Three languages where WF32 had one

| | WF32 | WF64 |
|---|--:|--:|
| Forth | 15,526 | 2,234 |
| Assembly (hand-written) | — | 11,863 |
| Assembly (generated Win32 bindings) | — | 39,084 |
| Rust | — | 30,007 |
| **Total (excl. generated)** | **15,526** | **44,104** |

WF32 is one language, self-hosted, no external toolchain. WF64 is Rust hosting a
`.masm` kernel through an LLVM-backed assembler, with a thin Forth library on top
— and about three times the code before you count the 39,000 lines of generated
Win32 bindings sitting on disk.

That comparison is unfair in one direction and unfair in the other. Unfair to
WF64 because 19,625 of those Rust lines are **iGui**, a Direct2D/DirectWrite MDI
IDE that WF32 never attempted. Unfair to WF32 because WF32 built its own PE
writer, its own image manager and its own turnkey generator in that 15,526 —
things WF64 simply doesn't do (its README is explicit: _"exe generation is not a
priority; native code generation is"_).

But the middle of the table is the real story: **11,863 lines of hand-written
assembly, and 519 `proc()` definitions**, to express a kernel that WF32 expressed
in Forth-with-an-assembler. The `.masm` files are good — well commented, clearly
structured, with a register-convention banner repeated at the top of every file
because RAX-is-TOS is the kind of invariant that will bite you at 2am. But they
are inert text. You cannot extend them from the REPL.

## The kernel: STC, widened

The register assignment came across intact. `kernel/macros.masm` says so at the
top — _"carried over from the WF32 plan"_:

| role | WF32 | WF64 |
|---|---|---|
| top of stack | `eax` | `rax` (`TOS`) |
| data stack pointer | `ebp` | `rbp` (`DSP`) |
| user area pointer | `ebx` | `rbx` (`UP`) |
| return stack | `esp` | `rsp` — still the CPU stack |
| scratch | `ecx`, `edx` | `rcx`, `rdx`, `r8`–`r11` |

And the primitive shape survived, macro for macro:

```
; WF32                          ; WF64
code dup ( n -- n n )           proc(dup_)
    1 2 in/out                      mov [DSP - cell], TOS
      mov { -cell ebp } eax         stk(1, 2)
      next; inline                  next()
                                endp()
```

`stk(in, out)` is WF32's `in/out` annotation with a new name, doing exactly the
same job — emit `sub rbp, (out-in)*cell`, or `add`, or nothing. `next()` is
`ret`, and the macro's comment keeps WF32's name on purpose: _"Named for
compatibility with WF32 idiom even though in STC there is no inner-interpreter
NEXT loop."_

One small thing to notice, because it is the shape of everything that follows:

```
@rust_macro stk
```

`stk` has to do arithmetic over its arguments, and JASM's macro processor is a
token-stream expander with no arithmetic. So `stk` is implemented **in Rust**,
inside the assembler. In WF32, `next;` computed the same adjustment in Forth,
inside the Forth, at compile time, using the Forth's own arithmetic. The
capability didn't disappear; it moved to a place you need a Rust rebuild to
reach.

## The header: WF32's `head%`, transcribed

This is where the inheritance is most literal. WF64's `macros.masm` says it
plainly — _"WF64 now models WF32's real header shape rather than the earlier
mini-header"_ — and the fields line up one for one:

| WF32 `head%` | WF64 `dh_*` | offset | meaning |
|---|---|--:|---|
| `head.link` | `dh_link` | `0x00` | previous header |
| `head.ct` | `dh_ct` | `0x08` | `compile,` or `execute` |
| `head.xtptr` | `dh_xtptr` | `0x10` | the xt |
| `head.comp` | `dh_comp` | `0x18` | **how to compile me** |
| `head.rec` | `dh_rec` | `0x20` | recognizer |
| `head.vfa` | `dh_vfa` | `0x28` | source line |
| `head.ofa` | `dh_ofa` | `0x2A` | body length, for inlining |
| `head.stk` | `dh_stk` | `0x2C` | stack effect |
| `head.tfa` | `dh_tfa` | `0x2E` | type flag |
| `head.nt` | `dh_nt` | `0x2F` | counted name |

Cells widened from 4 to 8; the three 16-bit fields and the type byte stayed
exactly as they were. The xt-side backoffset cell — WF32's trick of storing a
displacement at `xt - cell` so any xt can find its own header in constant time —
came across too, and on the primitive side WF64 has to do something WF32 never
did: the primitives live in MCJIT-finalized pages, so Rust has to
`VirtualProtect` the page RWX, poke the backoffset in, and restore protection.

The candid part is in `docs/dict_header.md`:

> `dh_comp` still mirrors the generic `compile,` path rather than a distinct
> `xt-call,` action

So the header is a faithful copy, and for a while the most important field in it
was dead. WF32's entire compiler is `compile,` = `dup >comp perform` — ask the
word how to compile itself. WF64 shipped the field and dispatched through
`dh_ct` regardless. The design was inherited as *structure* before it was
inherited as *mechanism*: a fossil in the dictionary, waiting.

## Losing the inliner, and the three attempts to get it back

### Attempt one: hand-poked bytes, one word at a time

The first inlining in WF64 is not a mechanism, it is 22 hand-written procedures.
Here is the whole of `inline-dup,`:

```
proc(inline_dup_comp)
    mov     r8, [UP + user_HERE]
    mov     byte ptr [r8 + 0], 0x48          ; mov [rbp-8], rax
    mov     byte ptr [r8 + 1], 0x89
    mov     byte ptr [r8 + 2], 0x45
    mov     byte ptr [r8 + 3], 0xF8
    mov     byte ptr [r8 + 4], 0x48          ; sub rbp, 8
    mov     byte ptr [r8 + 5], 0x83
    mov     byte ptr [r8 + 6], 0xED
    mov     byte ptr [r8 + 7], 0x08
    add     r8, 8
    mov     [UP + user_HERE], r8
    ...
```

Its comment calls it _"first real WF32-style inline compile helper."_ There are
21 more like it — `drop`, `swap`, `over`, `>r`, `r>`, `r@`, `2>r`, `2r>`, `2r@`,
`i`, `j`, the two `do` halves, the branch primitives, the loop primitives,
`unloop`.

Compare what the same thing costs in WF32:

```forth
code dup ( n -- n n )
    1 2 in/out
      mov { -cell ebp } eax
      next; inline
```

One word. WF32 already had an assembler, so the primitive's *own body* is the
inline expansion, and `inline` just says "copy it." WF64 has an assembler too —
but it runs at kernel-build time, in a different process phase, and cannot be
reached from a running Forth. So the expansion has to be hand-encoded as literal
opcode bytes in a second, parallel copy of each primitive.

Two copies of `dup` that must agree, in hex. That is a maintenance liability, and
it is the direct consequence of the assembler being a build-time tool rather than
a resident one.

### Attempt two: the generic mechanism, restored

Eventually `(inline,)` appears — and it is WF32's `inline,`, arrived at
independently:

```
proc(inline_comma_word)
    mov     r9, TOS                          ; r9 = xt
    mov     rdx, [r9 - cell]                 ; xt-side backoffset
    add     rdx, r9
    sub     rdx, dh_ct                       ; = header base
    movzx   r8, word ptr [rdx + dh_ofa]      ; length-to-inline
    test    r8, r8
    jz      .fallback_call
    mov     rsi, r9
    mov     rdi, [UP + user_HERE]
    mov     rcx, r8
    rep     movsb
```

Read `dh_ofa`, `rep movsb` that many bytes, fall back to a `call` if the length
is zero. That is `dup >name head.ofa w@ copy-code` in x86-64. The dormant field
woke up.

And the `inline` declarator, now written in Forth in `lib/core.f`, measures the
body the same way WF32 does — `HERE - xt - 1`, _"excluding the trailing RET that
`;` emitted"_. Same off-by-one, same reason, arrived at from the same
constraint.

### The guard, and where the two systems really diverge

Copying a body is only safe if it contains no relative call or jump out of
itself. Both systems know this. They find out very differently.

**WF32** knows because it was *told*. `xt-call,` writes `code-here` into a
`tail-call` variable every time it emits a `call`; `:` zeros it. At `; inline`,
`tail-call 0=` is a *proof* that no call was emitted in this definition. The
information was captured at the moment it existed.

**WF64** throws that information away by emitting first, and then goes looking
for it in the bytes:

```forth
\ (inline-leaf?) ( xt len -- flag )
\ True iff the body [xt, xt+len) contains no relative CALL/JMP byte …
\ Heuristic but conservative: a spurious 0xE8/0xE9 inside an immediate
\ only costs a missed inline (safe CALL).
: (inline-leaf?)  ( xt len -- flag )
    over + swap
    begin 2dup u> while
        dup c@  dup $E8 = swap $E9 = or
        if 2drop false exit then
        1+
    repeat 2drop true ;
```

A byte scan for `0xE8`/`0xE9`. It is honest about being a heuristic — an `0xE8`
appearing inside an immediate operand will produce a false positive and cost you
an inline you could have had. It's conservative in the safe direction, and it
works. But it is a machine looking at its own output through a keyhole, guessing
at a fact it knew for certain thirty microseconds earlier and did not write down.

That one contrast is the whole article in miniature.

Note also what WF64 gets *right* that WF32 didn't have to think about: because the
runtime `inline` declarator now checks leafness itself, it is safe to apply to
anything — leaf bodies inline, non-leaf bodies quietly fall back to a call. WF32's
guard is stronger, but WF64's is applied more uniformly.

## The tail-call variable survived intact

`user_TAIL_CALL` sits at offset `0x17D8` in the user area, described in the source
as _"HERE just after the most recently emitted CALL (0 if not preceded by a fresh
CALL). Used by `;` and `EXIT` for tail-call optimisation."_ That is WF32's
`tail-call`, transplanted whole.

And `;` does the same one-byte rewrite:

```
    cmp     r8, [UP + user_TAIL_CALL]
    jne     .no_tco
    mov     byte ptr [r8 - 5], 0xE9        ; E8 → E9: CALL becomes JMP
.no_tco:
    mov     byte ptr [r8], 0xC3            ; RET
```

Where WF64 goes further than WF32 is in discovering the exceptions the hard way.
Two of them:

**TCO-unsafe primitives.** `rdrop`, `2rdrop`, `n>r`, `nr>` manipulate the return
address themselves. Patch the `call` before one into a `jmp` and it inherits the
caller's return frame and crashes. WF64's answer is a second emitter,
`compile_comma_no_tco`, wired in as those four words' compile helper — and it
doesn't just decline to set the flag, it actively *zeroes* it, so an earlier safe
`CALL` can't be tail-called across the unsafe one.

**Locals frames.** A definition with locals must release its frame before
returning, so `emit_locals_release` runs first and advances HERE past the
tail-call slot — which means the `cmp` fails naturally and TCO only fires for
leaf-frame words. A correctness property falling out of ordering rather than a
check. Neat, and slightly alarming.

WF32 has neither problem: it has no locals in the kernel, and its return-stack
primitives are inlined rather than called.

## Literal folding: the road not taken

This is the sharpest divergence, and the one with the longest consequences.

**WF32 doesn't emit literals.** `' litstack compiles-for literal` makes `literal`
push its value onto a compile-time stack and emit nothing. `sync-code` flushes
whatever is pending when real code must be generated. Between those two points
the compiler is holding a window of *known constants as data*, and `+` can simply
ask "is there one?"

**WF64 emits the literal, then goes back for it.** A literal compiles to `call
do_lit` followed by an 8-byte inline value — 13 bytes. When `+` is later
compiled, its helper has to reconstruct the situation by decoding what's already
in memory:

```
proc(try_fold_literal)
    mov     r8, [UP + user_HERE]
    cmp     byte ptr [r8 - 13], 0xE8         ; CALL opcode?
    jne     .no
    mov     edx, dword ptr [r8 - 12]         ; rel32 of the CALL
    movsxd  rdx, edx
    add     rdx, r8
    sub     rdx, 8                           ; = call target
    lea     r9, [rip + do_lit]
    cmp     rdx, r9
    jne     .no                              ; CALL doesn't target do_lit
    mov     rcx, [r8 - 8]                    ; the literal value
    movsxd  rdx, ecx
    cmp     rdx, rcx
    jne     .no                              ; doesn't fit in signed imm32
    sub     r8, 13                           ; rewind HERE
    clc
    ret
```

It reads back its own opcode byte, sign-extends its own rel32, recomputes the
call target, compares it against `do_lit`'s address, re-reads the value, checks
it still fits in an imm32, and only then rewinds HERE by 13 bytes so the caller
can emit `add rax, imm` in its place.

That works. It ships. `2 3 +` folds. There are **19** of these fold helpers —
`+ - * and or xor lshift rshift arshift` and ten comparisons — each with an imm8
and an imm32 encoding path, each written as literal `mov byte ptr [r8+n], 0x…`
sequences.

Against WF32's:

```forth
: opt@  ( xt -- ) lits>0? if litstart push-tos var->tos else inline, then ;
' opt@ compiles-for @
```

Same optimisation. One has to disassemble itself to find out what it did; the
other never let go of the answer.

## Where the optimiser lives

There is one more structural difference, and it is the one I'd fix first if I
went back.

In WF32, installing an optimiser is a line of Forth in a file loaded *after* the
kernel:

```forth
' opt!     compiles-for !
' opt@     compiles-for @
' opt/     compiles-for /
```

No rebuild. No kernel change. You can do it at the REPL. The whole
`optliterals32.fs` layer is retrofitted onto a finished kernel from outside.

In WF64, it is a `match` arm in `src/lib.rs`:

```rust
fn primitive_comp_helper(&mut self, asm_sym: &str) -> Result<Option<u64>> {
    let helper = match asm_sym {
        "dup_"   => Some("inline_dup_comp"),
        "drop_"  => Some("inline_drop_comp"),
        ...
        "plus"   => Some("fold_plus_comp"),
        "minus"  => Some("fold_minus_comp"),
        ...
        "rdrop"  => Some("compile_comma_no_tco"),
```

45 arms, resolved through MCJIT `lookup_addr` during Rust-side bootstrap. It is
clean, it is greppable, and changing it means recompiling Rust and restarting the
process. The extension point moved out of the language and into the host.

To be fair to it: WF64's own design critique spotted this and counted it as a
plus — _"per-primitive `dh_comp` is data, not control flow"_ — because it means a
future optimiser can be bound in mechanically. It's right. The table is data. It's
just data that lives on the wrong side of a compile.

## What WF64 has that WF32 never did

I've spent most of this article on what the port cost, so here is what it bought,
and it is not a short list.

- **A 128 MB near region.** The Rust driver uses `VirtualAlloc2` with
  `MEM_ADDRESS_REQUIREMENTS` to place the data stack, return stack, user area and
  dictionary heap within ±2 GB of the JIT'd kernel, so **every `call rel32`
  always fits**. STC on a 64-bit address space needs this or it needs
  trampolines; WF64 chose placement over indirection, which is the right answer
  and one WF32 never had to find.
- **451 primitives** registered from Rust, **519 `proc()`s** in the kernel.
- **The ANS Forth-2012 core suite passing**, M1 through M7, plus **353 Rust
  integration tests** in a 5,582-line harness that boots a session, feeds it
  script, and asserts on output. WF32's testing story is nothing like this.
- **A paged garbage collector** (`newgc-core`, shared with the Lisp and the other
  compilers on that substrate) giving a managed heap outside the dictionary, and
  on top of it **1,893 lines of managed dynamic strings**.
- **`CODE:` … `;CODE`** — a runtime escape hatch that assembles a new primitive
  from `.masm` text through JASM into a near code arena, and points a dictionary
  header at it. This is WF64 partially recovering WF32's resident assembler.
- **`LET`** — an infix floating-point expression compiler emitting
  register-allocated SSE, 1,890 lines of Rust. The Mandelbrot demo ships both a
  hand-written MASM escape loop and a `LET` version of the same arithmetic
  specifically so you can A/B the two codegen paths.
- **Locals**, a single-inheritance **object system**, catch/throw, wordlists and
  search order, a dictionary overlay with hashed lookup.
- **iGui** — a 19,625-line Direct2D/DirectWrite/D3D11 MDI IDE with REPL panes, a
  live stack viewer, a source editor, a log pane, an in-window Markdown+Mermaid
  documentation browser, and a VEH crash dumper.

That last one deserves its own note: WF32's environment is a console, and it is
extraordinarily open. WF64's environment is a real Windows IDE, and it is closed
— you cannot edit iGui from the Forth. Both directions are a real trade.

## The LLVM bill, paid in instalments

The line I've used elsewhere in this portfolio — "a Forth embedded inside an LLVM
macro assembler" — is literal. JASM at this point encoded through LLVM-MC and
loaded through MCJIT, so a Forth REPL dragged a full LLVM behind it.

The measurements, from the commits that attacked it:

| build | `LLVM-C.dll` |
|---|--:|
| stock (C:\Program Files\LLVM) | 67.7 MB |
| `LLVM_TARGETS_TO_BUILD=X86` only | 42.1 MB |
| \+ `MinSizeRel` | 34.4 MB |
| \+ UPX `--best --lzma` | **10.2 MB** |

The shipped release folder went **71 MB → 13 MB**. LTO was tried first and failed
interestingly: MSVC's LTCG dead-stripped the llvm-shlib export list and produced a
10 KB stub DLL.

Getting to 15% of stock is a good piece of work, and it is also the clearest
possible signal that the dependency was wrong. You do not spend twelve minutes of
Ninja and 32 GB of build directory shaving a library you're happy with.
[WF65](/posts/wf65) — begun 2026-06-08, while WF64 was still the tip — demoted
LLVM from the default backend to a byte-exact oracle, and
[WF66](/posts/wf66) removed it outright two days later.

## The design doc that predicted WF66

Sitting in `docs/design/` are five documents about a Forth-aware optimiser,
including two adversarial critiques of the proposals. They are the most valuable
thing in the repository, because they diagnose WF64 from the inside while it was
still running.

The v1 doc's own verdict on the "make JASM recognize its own idioms" idea:

> **The Forth-aware pass cannot be a peephole over emitted x86.** There is no x86
> in JASM's hands — only tokens that *spell* x86. Recognizing "a spill followed by
> a reload cancels" by pattern-matching token lines is brittle … and re-derives
> information we *already have* at the moment we choose which op to emit.

And its conclusion:

> the optimizer must run at the lowering layer, before text exists, as a Rust pass
> over an explicit op vector … We make that decision *abstract* — emit a typed op,
> not bytes — run a small stack-caching optimizer over the op vector, and only
> then render the surviving ops.

That is **[WF66](/posts/wf66)**, described a month before it was built. Capture
the definition as a token IR, optimise the tokens as data, emit last.

It is also — and I don't think the doc noticed — a rediscovery of what WF32 was
already doing. WF32's deferred-literal stack *is* "information we already have at
the moment we choose what to emit." WF32 didn't have a typed op vector, but it
had the principle: **don't emit until you know**. WF64 emitted first and spent its
whole life reading its own output back.

The adversarial critique is even better, and lands one line I keep coming back to:

> the *framing* ("JASM-aware macro assembler") is a fig leaf over what is, by the
> doc's own architecture, a tiny Forth compiler in Rust.

Correct. And once you accept that, WF65 and WF66 are obvious.

## What works today

Grounded, not aspirational:

- **M1–M7 all complete.** Boot → REPL → colon compiler → control flow →
  `INCLUDE` → **ANS Forth-2012 core suite passes**. `cargo test` green including
  `m7_ans_core_tests_pass`.
- **451 primitives**, **1,042 lines** of `lib/core.f` on top, plus the object
  system in `lib/oop.f`.
- Fourteen demos ship in the release, including two Mandelbrots, a Julia set, a
  million-iteration loop benchmark, an OOP shapes demo and a strings tour.
- The gap analysis (2026-05-25) is candid about what's left: _"The main remaining
  gaps are no longer in the basic core language; they are in the broader FILE,
  MEMORY, and FLOAT extensions."_

## Download & run

Prebuilt Windows binaries: the
[GitHub Releases page](https://github.com/albanread/WF64/releases). The release
folder is `wf64-ui.exe` plus `LLVM-C.dll` (which must stay alongside it),
`kernel/`, `lib/`, `demos/` and `docs/`. The kernel is assembled from `.masm`
source at every boot — moving the folder is fine, breaking the layout is not.

```bash
git clone https://github.com/albanread/WF64
cd WF64
cargo build --release
```

Note the path dependencies in `Cargo.toml`: `wfasm` (JASM) and `newgc-core` are
sibling checkouts, not crates.io packages. This was a co-evolving family, not a
set of released libraries.

## Notes, dead-ends, lessons

**Port the mechanism, not just the structure.** WF64 copied WF32's header
faithfully and left `dh_comp` inert for months. The ten fields were there; the
one-line `compile,` that made them mean something was not. A data structure
without the dispatch that reads it is decoration.

**An assembler you can only reach at build time is half an assembler.** Every
hand-hexed `mov byte ptr [r8+3], 0xF8` in `compile.masm` exists because the
running system couldn't call the assembler it was built with. `CODE:` fixes this
partially and late. WF32's answer — the assembler is a vocabulary, always present
— is better, and the whole line spent the next two projects working back toward
it.

**Don't emit what you might want to change.** This is the one that generalises
past Forth. WF64's folder decodes its own rel32 to check whether the call it
emitted 13 bytes ago went to `do_lit`. Every one of those checks is a fact the
compiler had and discarded. WF65 industrialised the workaround (rewind and
replay); WF66 fixed the cause (don't emit until the tokens are optimised); MF66
carried the fix to Apple Silicon.

**Three weeks is enough to pass the ANS core suite, and not enough to be fast.**
Both of those are worth knowing.
