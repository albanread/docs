_[WF65](/posts/wf65) optimized by emitting code and then rewriting it. WF66 doesn't
emit until it knows — which is the thing [WF32](/posts/wf32) was already doing in
2005, finally rebuilt with an IR underneath it._

## TL;DR

- **What:** a token-IR optimizing **Forth**, successor to [WF65](/posts/wf65).
  Six days, 84 commits. Keeps WF65's runtime substrate — JASM/Rasm native
  encoding, the STC kernel, the dictionary, the REPL, the harness — and
  **replaces the compiler**.
- **The change in one line, from the README:** WF65 emits eagerly then *replays*
  (rewind + rewrite) to optimize; **WF66 captures each definition as a token IR,
  optimizes the tokens as data, and only then generates code.**
- **Two reducers, one idea.** Level 1 rewrites the token stream to a fixpoint.
  Level 2 lexes the lowered asm back into instruction records and rewrites
  *those*. **No SSA, no CFG, no register allocator** — the early design docs
  proposed all three and were deliberately abandoned as "a fraction of the
  machinery" for most of the win.
- **Two sources of truth.** The eager WF65 compile still runs underneath every
  definition. WF66 only ever *replaces* a body it fully understands
  (`is_deferrable`); anything it can't model leaves the eager body standing. The
  optimizer is structurally unable to produce a wrong program.
- **Measured:** 3.7× over the eager STC baseline on the bench loop; a pure-Forth
  Mandelbrot inner loop lands **~2.6× off hand-written MASM**, with the residual
  identified as one specific thing (loop-carried register residency) and left
  open on purpose.
- **Verified by its predecessor.** WF65 is the differential oracle: a
  **600-program fuzzer**, the ANS core suite run *both* eager and optimized, 433
  harness tests, and a committed **517-symbol byte golden** of the whole kernel.
- **Get it:** [Downloads](#download-run) · [Source](https://github.com/albanread/WF66)

## Where it sits

[WF32](/posts/wf32) → [WF64](/posts/wf64) → [WF65](/posts/wf65) → **WF66** →
[MF66](/posts/mf66) → [MF67](/posts/mf67). WF66 is the compiler-architecture
turning point that MF66 then carried onto Apple Silicon. See the
[timeline](/timeline).

The three articles before this one describe a system that kept trying to read its
own output. [WF64](/posts/wf64) decoded its own `rel32` to find out whether the
`CALL` it emitted thirteen bytes ago went to `do_lit`. [WF65](/posts/wf65)
industrialised that into a scan-back peephole and measured it honestly — and its
`do_lit_count` metric never moved across nine commits of optimisation, because
you cannot un-emit a literal you have already emitted. WF66 is the commit where
that stops.

## What it actually replaced

The README is unusually direct about what *didn't* get built:

> Early design notes proposed a heavier CFG/SSA/cross-block-register-allocation
> architecture; that was **not** the path taken — WF66 is a pattern-rewriter plus
> a deferred-assembly buffer, which got most of the win for a fraction of the
> machinery. Those stale plan docs have been removed.

I want to flag that as the most important engineering decision in the project,
because it is the one that would have sunk it. [WF64's own design
docs](/posts/wf64) prescribed a typed op vector and a stack-caching optimizer,
and a full SSA/CFG/regalloc pipeline is the obvious next escalation. WF66 read
its own proposal, took the *shape* (optimise before emit), and refused the
machinery. What shipped is:

```
Forth source
   │  outer interpreter drives the IR builder        ── capture
   ▼
[Token]  ── per-definition token IR
   │  reduce()                                        ── LEVEL 1 (Forth level)
   ▼
[Token] reduced
   │  lower()                                         ── tokens → Intel asm text
   ▼
asm text
   │  parse_instrs()                                  ── lex back into records
   ▼
[Instr]
   │  fp_coalesce → coalesce_dsp →                    ── LEVEL 2 (machine level)
   │  window_fuse → promote_hot_cells
   ▼
[Instr] reduced
   │  render() ; wfasm::rasm::assemble()              ── native encoder
   ▼
machine code  → patched over the eagerly-compiled body
```

The whole optimizer is a pure function `tokens -> bytes` in one 3,573-line Rust
module.

## Part 1 — capture, and the safety net that makes it possible

**WF66 does not parse Forth.** That sounds like a limitation and is actually the
central trick. The existing WF65 outer interpreter still compiles the definition;
as it does, kernel convergence hooks call a Rust recorder *alongside* emitting
bytes. `rt_ir_begin` at `:`, `rt_ir_word` per compiled word (by xt), `rt_ir_lit`
for literals, `rt_ir_finalize` at `;`.

So there is no front end. The Forth stays in charge of being Forth — the outer
interpreter, immediate words, `CREATE`/`DOES>`, the whole reflective surface —
and the optimizer is a passive observer that gets handed a `Vec<Token>`.

The consequence is the design decision I'd steal:

> The eager WF65 compile still runs underneath, so there is always a correct body
> to fall back to.

`is_deferrable()` checks that every token is in the modelled set. If a single
`Opaque` appears — an unknown word, an immediate word's emission, a `CODE:`
region, a raw byte poke — `compile_body_bytes` returns `NotDeferrable` and the
eagerly-compiled body simply stands. WF66 only ever *replaces* a body it fully
understands.

That is a categorically different safety posture from its ancestors. WF65's
scan-back fusion had to *argue* that an 8-byte signature couldn't alias a `CALL`'s
`E8`. WF32's `inline` had a proof (the `tail-call` variable) but the proof was
bespoke. WF66 needs neither, because a span it doesn't understand is a span it
doesn't touch. The current taint set is honestly documented — `do`/`loop`, I/O,
return-stack ops, FP comparisons — with `begin`/`until` and float locals handled.

## Part 2 — level 1: the token-IR reducer

`reduce()` is a shift-reduce fixpoint engine, and it is six lines:

```rust
pub fn reduce(tokens: &[Token]) -> Vec<Token> {
    let mut out: Vec<Token> = Vec::with_capacity(tokens.len());
    for &t in tokens {
        out.push(t);
        reduce_tail(&mut out);
    }
    out
}
```

Shift a token; reduce the tail until nothing fires; repeat. Because every
reduction shortens the tail and the new tail is immediately re-checked, one
forward sweep reaches a fixpoint — including cascades.

All the intelligence is in a rule table, `reduce_pair`, which reads like a
Forth-idiom dictionary:

```rust
// DCE: a side-effect-free producer then drop -> nothing
(Lit(_) | Stack(Dup) | Stack(Over), Stack(Drop)) => vec![],
// common idiom -> rarer single-op equivalent (Forth favors common ops)
(Stack(Swap), Stack(Drop))  => vec![Stack(Nip)],      // swap drop = nip
(Stack(Over), Stack(Over))  => vec![Stack(TwoDup)],   // over over = 2dup
(Stack(Swap), Stack(Swap))  => vec![],                // identity
// literal folded into an op -> register-immediate op
(Lit(k), Inline(op)) if fits_i32(k) => vec![ImmOp { op, k }],
// dup + binary op -> self-combining op (a+a, a*a, ...)
(Stack(Dup), Inline(op))    => vec![DupOp(op)],
// comparison feeding a flag test -> branch off the operand directly
(Cmp(c), Ctl(If | Until | While)) => vec![CmpCtl(c, ctl)],
// two same-op immediates collapse (7 + 3 + -> +10)
(ImmOp{op: o1, k: k1}, ImmOp{op: o2, k: k2}) if o1 == o2 => …
```

The comment on `reduce` names the payoff precisely:

> Subsumes const-fold / DCE / imm-fold / dup-fuse / compare→branch as one rule
> table run to fixpoint, and catches the cascades a fixed-order pipeline misses
> (`7 + 3 + -> +10`, `1+ 1+ 1+ 1+ -> +4`, `2 dup * -> 4`). **Whole-definition
> visibility is what makes this possible.**

Compare the same three cascades against WF65. `2 dup *` in WF65: `2` becomes
`call do_lit; .quad 2`; `dup` gets inlined; `*` scans back, finds an inline-`dup`
signature, fuses to `imul rax,rax`. It cannot then notice that its operand was a
constant, because the constant is already thirteen bytes of emitted machine code
behind it. WF66 reduces `Lit(2), Stack(Dup), Inline(Mul)` → `Lit(2), DupOp(Mul)`
→ `Lit(4)`. One token.

There is also a detail I find quietly excellent: **the rule catalog is ordered by
a frequency miner.** `cargo run --bin seq_freq` walks every `:`…`;` body in
`lib/`, `demos/` and `bench/corpus/`, plus every `proc`…`endp` in the kernel
MASM, and reports the top bigrams and trigrams. The rules exist because those
sequences are actually common in this codebase's Forth — not because they were
easy to write.

## Part 3 — level 2: "we have our own assembler, so we defer assembly"

The second reducer is the one with no precedent anywhere earlier in the line.
Rather than hand the lowered asm text to the encoder, WF66 lexes it into
instruction records and rewrites *those*.

**`coalesce_dsp`** defers every data-stack-pointer adjustment to the edge of a
barrier-free window, rewriting each cell displacement by the running delta as it
goes. Paired push/pop adjusts cancel; a whole shuffle run's adjusts collapse to
one. Note the comment on the arithmetic case — a `Fop` reads a stack cell but
leaves `rbp` alone, so it is *not* a barrier, which keeps `rbp` stable across a
whole basic block.

**`window_fuse`** is the best piece of code in the project:

> After coalescing, a barrier-free window is pure fixed-offset slot addressing.
> Rather than replaying each stack op's moves, recognize the *whole window* as a
> permutation/duplication pattern: symbolically simulate it to the net map …
> then emit the MINIMAL parallel-move that realizes it. `rot rot` (8 accesses)
> collapses to its net `-rot` (4); redundant reloads vanish; nothing is replayed.

It builds an abstract value model (`Val::Rax | Val::Slot(i64)`), simulates the
window, computes the net permutation, and emits a minimal parallel move. It also
knows when to refuse: unknown source register, a load/store after the coalesced
adjust, a scratch register the following barrier reads (checked against
sub-register aliases — `rcx` guards `ecx`, `cx`, `cl`, `ch`), or more live
temporaries than the spare pool holds. Any of those and the window is emitted
verbatim.

**`promote_hot_cells`** loads a read-only data-stack cell read twice or more in a
run into a reserved register (`r10`/`r11`) and reuses it. No liveness analysis,
no spills — when the pool is empty, it stops.

That is a register allocator's *effect* without a register allocator's
machinery, and it is exactly the kind of trade the "not the path taken" note is
about.

## Part 4 — reaching past the leaf

Three mechanisms stop a call from poisoning everything around it:

- **Settle-barrier calls.** The ABI is "settle everywhere" — TOS in `rax`, the
  rest of the data stack in memory, canonical at every call and control edge. So
  a call to a *known* word (libm, or another WF66-optimized word) is just
  *settle, call, resume*, and the optimizer keeps working on the windows either
  side. The README makes the nice observation that **no stack-effect analysis is
  needed**, because settle-everywhere already guarantees the invariant.
- **Variables are address pushes, not calls.** `create`'s stub bakes the body
  address in as `mov rax, imm64`; the recorder reads it back out and captures a
  literal. `var f@` then fuses to a direct absolute FP load. This is
  [WF65](/posts/wf65)'s `hotvariable` made automatic and unnecessary.
- **Optimized words inline.** A WF66-optimized word is a leaf by construction, so
  a caller either splices it or settle-barrier-calls it — never taints.

**Locals** are the subtlest part. A `{:`…`:}` frame lives on `R15`, and `{:`
records its own prologue into the IR through `(wf66-open-locals)` — it has to,
because `{:` *postpones* the frame ops and `postpone` compiles past the
recorder's capture point. `;` appends the paired teardown so the body is a
balanced `[OpenLocals … CloseLocals]` unit, and that balance is what lets a
locals word inline into another as a correct *nested* frame: `R15` dips and pops
while the caller's own locals stay untouched.

And the reason locals matter for optimisation is a property, not a heuristic: a
local is word-private and cannot be addressed, therefore **it cannot alias**. It
is the ideal promotion target, and the codebase says so in the `Token` enum
comment rather than leaving you to infer it.

## Part 5 — the numbers, and an unusually good scope argument

A pure-Forth Mandelbrot inner loop, `z = z² + c`, 5M iterations:

| variant | time |
|---|--:|
| Forth `fvariable`, optimizer **off** | ~153 ms |
| Forth `fvariable`, optimizer **on** | **~41 ms** (3.7×) |
| Forth float-locals, optimizer **off** | ~110 ms |
| Forth float-locals, optimizer **on** | **~42 ms** (2.6×) |
| hand-rolled MASM | ~16 ms |

The float-locals rows are the interesting ones: written the natural way — loop
state in named locals, whole loop in one word via `begin`/`until` — the optimized
result is *on par with* the tuned `fvariable` version. The idiomatic way to write
a hot loop is also the fast one, which is not usually how this goes.

Body-size deltas against eager WF65 (`wf66_size_report`): const-fold −8,
const-chain −12, inline −9, inc-chain −12, conditional body −13, loop body −16,
shuffle chains −8 — and never larger on the bench corpus. Contrast
[WF65](/posts/wf65), which paid **+7.5% bytes** for its call elimination. WF66
gets smaller *and* faster, because it never emits the code it would have had to
rewrite.

Then there is the residual 2.6× to hand-MASM, and the argument the README makes
about it, which I think is the most valuable paragraph in the whole repository:

> The hand-MASM … keeps `zx`/`zy` in `xmm0`/`xmm1` across the loop **only because
> it makes no calls**, so the Win64 volatile registers are genuinely free there.
> Register residency is only ever valid inside a **call-free region** … So *no*
> general-purpose program and *no* compiler can claim global register state; the
> call-free span is the universal boundary, full stop.

Which makes WF66's scope — leaf words and inlined hot paths — the *correct* one
rather than a limitation: it optimises exactly the regions where owning registers
is legal at all, which is the same boundary the hand-written assembly exploits.
The one thing MASM still does that WF66 doesn't is hold loop-carried state in
registers across a back-edge, and that is declared a deliberate stopping point:

> **The optimizer is feature-complete and this work is closed.** … any future
> optimization should be driven by a real corpus to analyze … not by speculative
> passes against hand-written micro-benchmarks.

Knowing where to stop, and saying so in the README, is rarer than the optimizer.

## Part 6 — WF65 as the oracle

[WF65](/posts/wf65) was frozen on purpose to be the yardstick, and WF66 uses it
exactly that way — but with a sharper contract than "same bytes":

> Identical source must produce identical *observable Forth state* (data stack,
> program-defined memory, output), even though WF66 emits different, faster
> bytes. It is a semantic cross-check, not a byte-for-byte spec.

The verification stack:

- A **600-program differential fuzzer**. Random deferrable programs — literals,
  arithmetic, derived ops, shuffles, comparisons, balanced conditionals — over
  random inputs, WF66's output checked against eager. Deterministic xorshift
  seed, so a failure prints the exact reproducing source. It deliberately
  excludes memory ops (random addresses fault) and loops (random conditions may
  not terminate) — a limitation stated rather than hidden.
- **The ANS Forth-2012 core suite run twice**: `m7_ans_core_tests_pass` and
  `m7_ans_core_tests_pass_with_wf66`. The optimizer must not change conformance.
- **433 harness tests** (WF65 had 353), plus differential tests for FP, libm,
  variable references, locals — including nested-frame inlining and
  `|`-uninitialized slots — and inlining.
- A committed **byte golden of the whole kernel**: 517 symbols, ASLR-normalised,
  in `bench/golden/kernel.json`, with a test that re-captures from the live build
  and diffs. Its comment is precise about what it proves: _"it proves the oracle
  is faithful before we ever trust it to gate the native `RasmEncoder`."_

That is [WF65's measurement gate](/posts/wf65) escalated one level. WF65 gated
codegen *metrics*; WF66 gates codegen *semantics* against a frozen implementation,
and gates the kernel's bytes against a committed snapshot.

## Part 7 — the four-project arc, stated plainly

This is the article where the line closes, so:

| | how a literal is handled |
|---|---|
| **[WF32](/posts/wf32)** (2005–2017) | never emitted — pushed onto a compile-time stack, flushed by `sync-code` when real code must appear |
| **[WF64](/posts/wf64)** | emitted as `call do_lit` + `.quad`, then recovered by decoding the emitted `rel32` and comparing it to `do_lit`'s address |
| **[WF65](/posts/wf65)** | same, industrialised: 19 hand-encoded fold helpers scanning back over emitted bytes. `do_lit_count` never improved |
| **WF66** | captured as `Token::Lit(i64)`; folded, cascaded and strength-reduced as data; emitted only if it survives |

WF32 got there in one step with a compile-time stack and 443 lines of Forth. WF66
got there with a typed IR, a fixpoint reducer and a second reducer over
instruction records. WF66's version is strictly more capable — WF32 could not
fuse `rot rot` into a parallel move, or promote a hot cell to a register, or model
a whole definition's cascades. But the *principle* is the one WF32 shipped
twenty years earlier: **don't emit until you know.**

It took two intermediate projects to get back to it, and both of them were
necessary: [WF64](/posts/wf64) proved the runtime, and [WF65](/posts/wf65) built
the measurement apparatus that makes WF66's claims checkable. Neither was wasted.
But the shortest description of this arc is that a 64-bit port lost an idea and
spent three projects re-deriving it — with the compensation that what came back
is better than what was lost.

## What else landed in six days

The optimizer is roughly the first two-thirds of the commits. The rest:

- **LLVM removed outright** (commit 2 of the project), completing the arc that
  [WF65](/posts/wf65) began by demoting it to an oracle.
- **Cooperative agents.** Win32-fiber green threads with mailboxes and a
  scheduler, so a "running" pane no longer stalls the console. The
  [design doc](https://github.com/albanread/WF66) is refreshingly disciplined
  about scope — _"This is explicitly NOT BEAM"_ — and keeps exactly two shaping
  choices (location-transparent agent IDs, copied messages) so it could later
  become N single-threaded Forths over a shared-memory bus without an API
  rewrite. Everything else is declined until there's a reason.
- **A `View` base class** and a pane-agent pattern, with every graphics demo
  converted to it.
- An **object system** with single inheritance.

Line counts, for the record: 38,612 lines of Rust (20,107 of it the iGui IDE),
13,608 of hand-written `.masm` kernel, 2,485 of Forth library — with the compiler
itself a single 3,573-line module.

## Download & run

Prebuilt binaries: the [GitHub Releases page](https://github.com/albanread/WF66/releases).

```bash
git clone https://github.com/albanread/WF66
cd WF66
cargo build --release
```

The optimizer is opt-in via `set_wf66_enabled`, default-on in the IDE (Forth →
WF66 Optimizer). The diagnostics are worth knowing:

```bash
cargo test --test harness -- --ignored --nocapture wf66_mandel_inner_bench
```

`wf66_compile_metrics` (coverage plus per-word min/max/avg of registers, bytes,
instructions and stack accesses), `wf66_register_stats` and `wf66_before_after_asm`
are in the same set. Path deps `../JASM/rust` and `../NewGC` resolve as in WF65.

Note that the package and binary are still named `wf64` from the fork — a
deliberate follow-up kept separate so the baseline stayed green.

## Notes, dead-ends, lessons

**Optimise as data, then emit.** The whole line is an argument for this. Three
projects tried to recover information from bytes they had already written; the
fourth kept the information instead. Everything else here is downstream of that
one decision.

**Keep a correct implementation running underneath the clever one.** The eager
WF65 compile still happens for every definition, and WF66 replaces the body only
when it fully understands the span. That converts "is the optimizer correct?"
from a proof obligation into a coverage question, and coverage is measurable.

**Refuse the machinery you don't need.** The design docs called for CFG, SSA and
cross-block register allocation. What shipped is two pattern reducers and got
most of the win. The abandoned proposal is documented as abandoned, which is the
right way to leave a fork in the road.

**Freeze a predecessor to check against.** A 600-program fuzzer is only possible
because something correct stayed still.

**Know where to stop, and write it down.** "The optimizer is complete" is in the
README, with the exact remaining gap named and the reason for not closing it. A
project that can state its own stopping condition is a project that finished.
