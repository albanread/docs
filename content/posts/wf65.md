_[WF64](/posts/wf64) ported [WF32](/posts/wf32)'s Forth and dropped its inliner on
the floor. WF65 is the three days spent picking it back up — but it builds the
scales before it touches the recipe, and that decision is the whole article._

## TL;DR

- **Shape:** a fork of [WF64](/posts/wf64), **19 commits over three days**
  (2026-06-08 → 06-10). Same kernel, same 353-test harness, same ANS core pass.
  What changed is codegen.
- **The first two commits after the fork are not optimisations — they are a
  measurement harness.** A corpus of pure-compute Forth, per-word static metrics
  taken by decoding the compiled body with `iced-x86`, checked-in golden JSON,
  and a CI gate that fails on a wrong-direction move.
- **Then nine straight kernel commits, every one an inlining commit.** Measured
  across the eight original corpus files: **CALLs 166 → 70 (−58%)**, bytes
  **2,479 → 2,666 (+7.5%)**.
- **That is WF32's trade, rediscovered by measurement.** WF32's `optinline.fs`
  header comment put it at roughly 10% more code space for a large speed win.
  WF65 measured +7.5% bytes for 58% fewer calls — two decades later, on a
  different architecture, arrived at from the opposite direction.
- **The method converged too.** After hand-encoding a dozen inline sequences,
  WF65 gives up and writes `inline_leaf_comp` — copy the leaf primitive's body up
  to its `ret` — because _"copying known-good, position-independent bytes is
  simpler and safer than re-encoding."_ That is WF32's `inline,`, argued into
  existence from scratch.
- **The biggest number in the project isn't an optimisation.** The dictionary was
  one `PAGE_EXECUTE_READWRITE` region, so every variable write next to code
  triggered a self-modifying-code machine clear. Splitting data into an RW
  no-execute region took a cold variable loop from **~34,000 to 238 cycles —
  about 143×**.
- **Get it:** [Downloads](#download-run) · [Source](https://github.com/albanread/WF65)

## Part 1 — the gate comes first

The file I'd point at if I could only show one from this repo is
`bench/README.md`, because it exists before any optimisation does:

> A deterministic before/after harness that gates the **Forth-aware optimizer**
> work on real codegen numbers instead of intuition. Compile a curated corpus,
> measure each compiled word's body, and compare against checked-in goldens so
> every optimizer change is a reviewable diff and any regression fails CI.

The corpus is ten files of headless, pure-compute Forth — one per transform the
optimiser is expected to perform, plus three real-world kernels (iterative Fib;
factorial / dot-product / djb2 hash; integer fixed-point Mandelbrot). Each is
written to stress exactly one thing. `stack-shuffle.f`, for the rbp-scheduling
transform, is blunt about it:

```forth
\ long-arith ( n -- m ) : ten consecutive `dup +` doublings — one unbroken spill
\ ladder. m = n * 1024.
: long-arith ( n -- m )
  dup +  dup +  dup +  dup +  dup +
  dup +  dup +  dup +  dup +  dup + ;
```

For each colon definition the harness records five gated metrics —
`byte_length`, `call_count_E8`, `jmp_count_E9`, `tail_is_jmp`, `do_lit_count` —
plus advisory instruction and `rbp`-adjust counts, and a rel32-normalised
`body_hash` as a "codegen changed at all" tripwire. Goldens are committed as
JSON, guarded by a kernel fingerprint and a per-file corpus hash so numbers from
two different kernels can never be silently compared.

And then there is the line that made me want to write this article directly after
the [WF64](/posts/wf64) one:

> All counts come from an iced-x86 **decode** bounded by `[start, end)`, **never
> a raw `0xE8`/`0xE9` byte scan**

WF64's `inline` declarator decides whether a body is safe to copy by walking it
looking for `0xE8`/`0xE9` bytes, and its own comment admits the heuristic
misfires when those bytes appear inside an immediate. WF65's measurement harness
opens by refusing to make that mistake: it pulls in a real x86-64 decoder, bounds
it to the word's body, and steps over `do_lit`'s inline `.quad` so the decode
stays aligned. The project's first act is to build an instrument more honest than
the compiler it is measuring.

There is a second, advisory layer: an rdtsc timing driver that runs each hot
word's loop **inside Forth** — one `call_xt` per rep bracketing an M-iteration
loop between two in-Forth RDTSC reads — so it times the word, not the Rust→Forth
boundary. Median over K reps, thread pinned, high priority. It is explicitly
given no authority: _"purely advisory: nothing here is asserted, and it has zero
authority over any exit code."_ Numbers you trust for direction, gated on numbers
you trust for truth.

The whole apparatus sits behind a cargo feature, so the decoder and hasher never
enter the shipping build graph.

## Part 2 — the campaign, in numbers

Because the goldens are committed, the history *is* the measurement. Here is
every blessed baseline across the eight original corpus files:

| commit | what landed | bytes | CALLs | JMPs |
|---|---|--:|--:|--:|
| `25105ef` | gate + corpus blessed — **the "before"** | 2,479 | **166** | 18 |
| `a30ecc0` | inline bare `+ - * @ !` | 2,738 | 102 | 9 |
| `25d0df5` | inline `rot -rot nip tuck c@ c!` | 2,800 | 96 | 7 |
| `633bca8` | fuse `dup +` / `dup *` | 2,618 | 96 | 7 |
| `a20b6c8` | comparisons / logic / shifts, generic | 2,620 | 95 | 7 |
| `3d5e1bc` | `1+ 1- negate 2* 2/ invert 2dup 2drop 2swap 2over` | 2,617 | 79 | 5 |
| `4d8e704` | `cells / mod /mod +!` | 2,666 | 70 | 5 |
| `4c4165a` | `min max abs` | 2,666 | **70** | 5 |

**166 → 70 calls, −58%. 2,479 → 2,666 bytes, +7.5%.**

Now put that beside the comment at the top of WF32's `optinline.fs`, recording
the same trade from a system written in the 2000s: inlining costs around 10% more
code space and buys "a 200% improvement in performance."

Two systems two decades apart, one 32-bit and one 64-bit, one measuring by
instinct and one by golden JSON — landing on the same exchange rate. I did not
plan that; I only noticed when I put the two numbers side by side for this
article.

Note also the column that *doesn't* move: `do_lit_count` sits at 26 for the
entire campaign. WF64's backwards-scanning literal folder was inherited
unchanged, and WF65 never improved it. That is the un-taken work — and it is
exactly the work [WF66](/posts/wf66) was built to do.

The commit messages carry the advisory timings, which are what you actually feel:

| word | new/old cycles | landed in |
|---|--:|---|
| `dot-prod` | 0.172 (**5.8×**) | bare-op inline |
| `str-hash` | 0.514 | bare-op inline |
| `long-arith` | 0.654 | bare-op inline |
| `fib-iter` | 0.762 | bare-op inline |
| `mandel-iter` | 0.694 | `dup *` fusion |
| `countdown` | ~0.74 | `1-` / `0=` inline |

## Part 3 — hand-encoding, and giving up on it

[WF64](/posts/wf64)'s inlining was 22 hand-written procedures, each spelling out
a primitive's bytes a second time:

```
mov     byte ptr [r8 + 0], 0x48          ; mov [rbp-8], rax
mov     byte ptr [r8 + 1], 0x89
mov     byte ptr [r8 + 2], 0x45
mov     byte ptr [r8 + 3], 0xF8
```

WF65 starts by doing more of that — `a30ecc0` and `25d0df5` add inline emitters
for `+ - * @ ! rot -rot nip tuck c@ c!` the same way. Then it reaches the
comparisons, and the arithmetic stops working. From `a20b6c8`:

> Rather than hand-encode 16 sequences (incl. the cmov-based signed compares),
> add a generic `inline_leaf_comp` that copies the leaf primitive body up to its
> `ret` — copying known-good, position-independent bytes is simpler and safer
> than re-encoding.

That is the argument for WF32's `inline,`, reconstructed from first principles by
someone who had just spent two days doing it the other way. Sixteen `jmp
compile_comma` fallbacks become `jmp inline_leaf_comp`, and from that commit on
the remaining inlining commits add *no kernel code at all* — `3d5e1bc` says so
outright: _"no new kernel code — it copies the leaf body."_ Ten more primitives
inline for the price of a table entry each.

WF32 reached that design in one step, because its primitives were already written
in a resident assembler and a primitive's own body therefore *was* its inline
expansion. WF64 and WF65 reached it across two projects and forty-odd commits,
because their assembler runs at build time and the running Forth can't call it.
Same destination; the route cost considerably more.

One nice consequence of going generic: `4c4165a` inlines `min`, `max` and `abs`
by first making them **branchless** — cmov-based `min`/`max`, a `cqo`/`xor`/`sub`
`abs`. The previous commit had explicitly excluded `abs` and `?dup` because both
branched. Rewriting a primitive so that it becomes inlinable is a different kind
of optimisation, and it only becomes an obvious move once the inliner is generic.

## Part 4 — fusion: the thing WF32 didn't do

`633bca8` is the one transform in WF65 with no WF32 ancestor. Once `dup` is
inlined, `dup +` compiles to a spill, a reload and two paired `rbp` adjustments —
to compute `TOS + TOS`. So the folder scans back for the 8-byte inline-`dup`
signature and, on a match, replaces the pair with one instruction:

- `dup +` → `add rax, rax`
- `dup *` → `imul rax, rax`

This is the best size result in the project: `long-arith` goes from **161 bytes
to 31** — the ten-step `dup +` ladder collapses to ten `add rax,rax` — and 182
bytes come off the corpus as a whole while the call count doesn't move at all.
`mandel-iter`, whose inner loop squares two fixed-point values, drops to 0.694 of
its previous cycles.

The commit is unusually careful about why the pattern match is safe: the 8-byte
inline-dup signature is distinctive, no other inline op's tail matches it, and a
`CALL`'s `E8` cannot alias at position −8. That reasoning is doing by hand the
job a real IR would do for free — which is, once again, the argument for WF66.

## Part 5 — `hotvariable`, and the bug underneath it

`9e9a5b9` adds `hotvariable`: a `variable` whose *references* compile to an
inline push of the body address rather than a `CALL` into the create stub. Opt-in
by design — _"the programmer tags the variables that are hot in an inner loop"_ —
which is a very Forth answer to a very Forth problem.

The measurement was startling. `hot-sum` against an otherwise-identical
`cold-sum`: **~34,401 → 372 cycles per iteration.** Roughly 90×, for removing one
call.

That number is far too large. A call/return is a handful of cycles, not thirty
thousand. The next commit, `edd3baa`, explains it — and it is the best thing in
WF65:

> The whole dictionary was `PAGE_EXECUTE_READWRITE`, so every variable/create
> body shared executable pages (and often a cache line) with its create stub. A
> `v ! … call v` loop therefore triggered a **self-modifying-code machine clear
> (~265 cyc)** on every reference — and all data was executable / all code
> writable (no W^X).

Writing to a variable was, as far as the CPU's front end could tell, patching
code. Every store next to executable memory forced a pipeline flush.

The fix is architectural, not peephole: move all data-space allocation — variable
and `CREATE` bodies — into a separate 16 MB `PAGE_READWRITE` no-execute region,
reached through an absolute address baked into each create stub. `here`/`allot`
operate on the new region with a bounds check that throws `-8` on overflow;
`>body` reads the baked address so it stays region-independent.

Result: **a cold variable loop drops from ~34,000 to 238 cycles, about 143×** —
and now every variable gets it, not only the tagged ones. `hotvariable` went from
a 90× optimisation to a modest one in a single commit, by having its premise
removed.

Two things I take from that:

1. **The biggest win in a compiler project is often not in the compiler.** Nine
   commits of careful inlining bought between 1.2× and 5.8×. One
   memory-protection fix bought 143× on a common pattern. That is the same lesson
   as [the Smalltalk-on-Dart work](/posts/optimizing-smalltalk-on-dart), reached
   from a completely different direction.
2. **The instrument found it.** `hotvariable`'s implausible 90× is what exposed
   the machine clears. Without a corpus and a cycle counter that is just a fast
   feature nobody questions. WF65 built the gate to catch regressions and it
   caught an architecture bug instead.

W^X is also the correct posture on its own terms — and it is the rule Apple
Silicon *enforces*, which the [MF66](/posts/mf66) port would shortly have to
satisfy anyway. WF65 arrived at it on Windows, for speed, by accident.

## Part 6 — the LLVM story, honestly

The line usually told about WF65 is "it dropped LLVM for a native encoder." That
is true, and it is mostly not in this repository.

The native x86-64 encoder (`RasmEncoder`), the LLVM-free loader (`NativeJit`) and
the differential oracle live in **[JASM](/posts/jasm)**, the assembler crate WF65
depends on as `wfasm = { path = "../JASM/rust" }`. JASM's own `Cargo.toml` states
the stance in a comment:

> **NATIVE IS THE DEFAULT.** A plain build compiles the front-end + native
> `RasmEncoder`/`NativeJit` … with NO LLVM-C dependency — the native loader is
> the working backend. `llvm` (opt-in) links LLVM-C … It now serves the
> differential **ORACLE** role: the only thing that keeps `RasmEncoder`
> byte-honest.

`oracle.rs` is explicit about its own status: it assembles the same text through
LLVM-MC into a relocatable object, parses it into the identical shape `rasm`
emits so the two can be diffed byte for byte, and is _"a build/test-time tool
only … nothing here is on the shipping native path."_ `NativeJit` maps its code
region **RW while relocating, then RX — never RWX**, which is the same W^X
discipline WF65's data-space commit arrived at independently, one repository
over.

WF65's `Cargo.toml` requests no features from `wfasm`, so it takes the native
default. That is the substance of the claim, and it holds.

Two caveats, stated because this blog is meant to be checkable:

- The design note both JASM and I would like to cite,
  `docs/design/rasm-replace-llvm.md`, is **referenced by JASM but not present in
  the public WF65 repository.** Its `docs/design/` folder carries the inherited
  WF64 optimiser proposals and nothing else.
- The committed `release/wf64/` folder is a **stale WF64 artefact** — the binary
  is still named `wf64-ui.exe` and its `README.txt` still tells you to keep
  `LLVM-C.dll` alongside it. WF65's own top-level `README.md`, by contrast, is
  genuinely rewritten, and describes the native plan in the future tense: _"Next
  phase for WF65, rebuild the assembler in Rust, drop the LLVM MC overhead, and
  get back to a 1MB size. Use the code generated by WF64 as the ORACLE."_

So: the encoder swap is real and it lives next door; this repo is a snapshot
caught mid-transition, with its release folder lagging its source. Worth saying
rather than smoothing over.

## What the author says the ancestor is

WF65's README does not make me work for the connection:

> From WF32 (one of my favourite Forths) the goldmine is obvious: WF32
> `src/optinline.fs` and WF32 `src/optliterals32.fs` — are the direct ancestors
> of the inline-helper and literal-folder here.

Those are precisely the two files [the WF32 article](/posts/wf32) is built
around: the 64-line inline optimiser and the 443-line deferred-literal folder.
WF64 inherited WF32's *structure* — the header, the ABI, the `tail-call` variable
— and left the optimiser behind. WF65 is where the optimiser gets collected.

## What's still wrong at the end of it

WF65 finishes fast, correct and measured, and still carries WF64's flaw — now in
a form the numbers make visible:

- **`do_lit_count` never moves.** Literals are still emitted as `call do_lit` +
  `.quad`, and folding still means scanning backwards over emitted machine code
  and decoding a rel32 to check where it points. WF32 never emitted them at all.
- **Every transform is a scan-back peephole.** The `dup`-fusion commit has to
  argue that an 8-byte signature can't alias. That argument is only necessary
  because the compiler discarded the fact that it had just emitted a `dup`.
- **Inlining decisions are still a `match` arm in Rust** binding an asm symbol to
  a helper symbol. Adding an optimisation means rebuilding the host, where WF32
  needed one line of Forth in a file loaded after the kernel.

[WF66](/posts/wf66) fixes the cause rather than the symptoms: capture each
definition as a **token IR**, optimise the tokens as data, and emit only at the
end. WF65 was frozen at that point on purpose — with a green gate, committed
goldens and a full corpus, it is the ideal thing to check a rewritten compiler
against. A project whose last job is to be the yardstick for its successor should
have measurements, and this one does.

## What works today

- Everything [WF64](/posts/wf64) had: M1–M7, the **ANS Forth-2012 core suite
  passing**, **353 integration tests**, the paged GC, managed strings, `LET`,
  `CODE:`, locals, the object system, the iGui MDI IDE.
- Plus the optimiser campaign above, `hotvariable`, and the W^X data-space split
  documented in `docs/memory-map.md`.
- Plus the measurement apparatus itself — a 464-line metrics core, a 190-line
  report/bless tool, a 227-line timing layer and a 57-line CI gate — which is the
  part I would most want to reuse.

The register file, with WF64's plus one addition:

| Reg | Role |
|---|---|
| `RAX` | TOS — top of data stack, always in a register |
| `RBP` | DSP — data stack pointer, grows down |
| `RBX` | UP — user-area base (callee-saved, survives Win32 calls) |
| `RSP` | return stack = the native call/ret stack |
| `R15` | LP — locals stack pointer |

## Notes, dead-ends, lessons

**Build the instrument before the thing it measures.** Two commits of harness
bought nine commits of confident optimisation, a reviewable diff per change, and
— unplanned — the discovery of a 143× architecture bug. If I could enforce one
habit across this whole portfolio, it would be this one.

**Make the instrument more rigorous than its subject.** The gate decodes; the
compiler byte-scans. That asymmetry is deliberate and it is the right way round.

**Suspicious wins are bugs in disguise.** A 90× speedup for removing one call is
not a triumph, it is a symptom. Chase it.

**Hand-encoding is a signal you're missing an abstraction.** Twelve hand-written
inline emitters, then one generic leaf-copy that made the next ten free. The
generic version is also the one WF32 shipped, which should have been a hint.

**Freeze things on purpose.** WF65 stopped at its peak and became a yardstick.
[WF66](/posts/wf66)'s claims are only checkable because something stayed still.
